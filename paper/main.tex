\title{Patch: State-Change Factorization and Semantic Change Contracts for Transparent Mutable Programs}
\author{Mich\'el Nguyen}
\date{Beta 6 research artifact manuscript, August 2026}

\begin{document}
\maketitle

\begin{abstract}
General-purpose languages usually expose mutation through assignment or data-structure-specific update operations, while systems for auditing, undo, provenance, replay, or policy enforcement reconstruct additional semantic structure around those writes. Patch explores the opposite factorization. Post-creation persistent mutation is represented and executed through a normalized semantic change. A programmer writes \texttt{change score: add 1}; the implementation constructs a structured delta identifying the target and semantic operation before committing the transition. We call the central design property \emph{State-Change Factorization}: every modeled persistent transition from $S$ to $S'$ factors through a semantic change $\delta$ satisfying $apply(\delta,S)=S'$, with no ordinary persistent-assignment escape hatch in the language core.

Patch derives \emph{Semantic Change Signatures} from this mandatory mutation representation and checks optional \emph{Change Capabilities} that constrain target, operation kind, and numeric magnitude. Thus a component may be authorized to increase \texttt{player.score} by at most 10 while remaining unauthorized to replace or decrease the same location. A Lean 4 model proves State-Change Factorization and Mutation Transparency, and a structured control-flow model proves Change Signature Soundness: every runtime semantic effect is contained in the statically inferred signature. This composes with policy admission to prove runtime capability containment.

Beta 6 strengthens the implementation boundary. A production-to-formal translation-validation layer independently reconstructs a small formal control-flow representation from the production AST for an explicit subset. A new executable Lean policy checker is proved sound with respect to the relational policy semantics. The production toolchain can emit a source-bound Lean certificate containing the translated statement and policy; formal CI compiles that certificate against the verified checker. The checker therefore does not trust the JavaScript production policy decision. The remaining critical trust gap is the JavaScript translation from Patch source/AST to the formal statement, which is explicitly outside the current theorem. Patch does not claim that effects, capabilities, range analysis, translation validation, proof-carrying evidence, provenance, or undo are individually new. The research question is whether mandatory semantic change provides a useful common substrate for quantitative mutation authority, formal assurance, and runtime tooling while preserving a deliberately small surface language.
\end{abstract}

\section{Introduction}
Mutable programs routinely need mechanisms that answer questions beyond ``what value is stored now?'' Debuggers need provenance, user interfaces need undo, event-sourced systems need replay, security mechanisms need to constrain effects, and collaborative systems need to reason about updates. In a conventional language, these facilities are commonly layered around writes whose semantic meaning is only partially represented by the language itself.

Patch asks what changes if the semantic update is primary. Instead of executing an assignment and later attaching metadata, a Patch program describes a change that is itself the route to the new persistent state:

\begin{lstlisting}
create number score = 0

change score:
  add 1
\end{lstlisting}

The surface syntax is intentionally small. Internally, however, the transition can carry target, operation, before/after state, version information, source location, and inverse information where available. This representation can support ordinary execution while also acting as a semantic observation point.

The same representation enables a more specific authority model than a binary write permission:

\begin{lstlisting}
allow reward:
  player.score may increase up to 10

make reward(player, bonus number 0..10):
  change player:
    add bonus to score
\end{lstlisting}

The policy permits an increase within a bound. It does not permit an arbitrary \texttt{set}, even though both operations write the same path. The production analyzer can use the declared input interval to derive a bound for the change amount.

The central research problem is not whether explicit changes, effect inference, or capabilities exist in prior work. They do. The problem is whether requiring persistent mutation to pass through one semantic change representation creates a useful factorization in which execution, static contracts, history, provenance, and formal checking share the same mutation vocabulary.

This manuscript makes five artifact-level contributions:
\begin{enumerate}[leftmargin=*]
\item a small language design in which post-creation persistent mutation has no ordinary assignment escape hatch;
\item a normalized Change IR and operation-/magnitude-sensitive Change Signatures and Capabilities;
\item a Lean model proving State-Change Factorization, Mutation Transparency, Change Signature Soundness, and runtime policy containment for a structured core;
\item a conservative production-to-formal translation-validation boundary for an explicit executable subset; and
\item a small executable Lean policy checker with machine-checked soundness and production-generated Lean certificates.
\end{enumerate}

The last two contributions must be read carefully. Beta 6 does \emph{not} prove the complete JavaScript compiler correct. It reduces and exposes the trust boundary: Lean checks the translated formal statement and policy, while the JavaScript source-to-formal translation remains an explicit proof obligation.

\section{Language Design}
\subsection{Progressive disclosure}
A beginner can ignore signatures, policies, proofs, and certificates:

\begin{lstlisting}
create number lives = 3
change lives:
  remove 1
show lives
\end{lstlisting}

Advanced facilities analyze the same state-change model instead of requiring the user to adopt a second event or command architecture.

\subsection{No persistent-assignment escape hatch}
\texttt{create} introduces a fresh binding. Existing persistent bindings cannot subsequently be updated with ordinary \texttt{x = e}. A state-changing program must use \texttt{change}. This syntactic restriction is not by itself a theorem, but it aligns the source language with the semantic commitment path.

\subsection{Semantic operations}
Current source operations are \texttt{set}, \texttt{add}, \texttt{remove}, and \texttt{clear}. The analyzer classifies numeric updates more semantically when possible. For example, \texttt{add 5} is an \emph{increase}, whereas \texttt{set 5} is a \emph{set}. Policies can distinguish these operations even when they target the same location.

\subsection{Console and GUI code share mutation semantics}
Patch UI handlers execute ordinary Patch code:

\begin{lstlisting}
create number count = 0

window "Counter":
  text "Count: {count}"
  button "Add" as add_button

when add_button clicked:
  change count:
    add 1
\end{lstlisting}

The current formal subset does not yet include GUI event execution, but the production runtime deliberately uses the same change machinery inside handlers.

\section{State-Change Factorization}
Let persistent state be a map $\sigma : Name \rightarrow Value$, let $\nu(x)$ be the current version of target $x$, and let history be $H=[\delta_1,\ldots,\delta_n]$.

A normalized semantic change is
\[
\delta = \langle x,b,n,v,\Delta,v'\rangle,
\]
where $x$ is the target, $b$ and $n$ are base and new versions, $v$ and $v'$ are before and after values, and $\Delta$ is an ordered sequence of semantic operations. Well-formedness requires
\[
applyOps(\Delta,v)=v' \quad\text{and}\quad n=b+1.
\]

Define one modeled persistent commit path:
\[
commit(\delta,\sigma,\nu,H)=
\langle\sigma[x\mapsto v'],\nu[x\mapsto n],H\cdot\delta\rangle.
\]

\paragraph{State-Change Factorization.}
For every state-changing step of the formal machine, Lean proves that there exists a well-formed $\delta$ such that the resulting machine is exactly the defined commit of $\delta$.

\paragraph{Mutation Transparency.}
As a corollary, the witnessing change is present in the resulting history. Thus a modeled persistent transition cannot occur without a corresponding semantic witness.

These are theorems about the current formal machine. A separate correspondence argument is required before they can be interpreted as theorems about every path through the production JavaScript runtime.

\section{Semantic Change Contracts}
\subsection{Change Signatures}
For a statement or recipe $f$, a Change Signature is a conservative set/list of semantic effects:
\[
Sig(f)=\{e_1,\ldots,e_k\}.
\]
An effect identifies a target, optional field, semantic operation kind, and optional amount interval.

For example:

\begin{lstlisting}
make reward(player):
  change player:
    add 5 to score
\end{lstlisting}

is summarized conceptually as
\begin{verbatim}
player.score -> increase by 5
\end{verbatim}

The production analyzer additionally handles simple transitive recipe calls. Unknown targets, recursion, or unsupported dynamic structure are treated conservatively in protected contexts.

\subsection{Magnitude-aware capabilities}
A capability policy specifies which semantic transitions are authorized:

\begin{lstlisting}
allow reward:
  player.score may increase up to 10
\end{lstlisting}

The production checker rejects a semantic operation not covered by a rule, a path not named by policy, or an amount whose proved upper bound exceeds the policy.

The quantitative aspect is important, but magnitude reasoning alone is not claimed as novel. The intended distinction is that the quantitative contract is attached to semantic transition kinds already required by the mutation representation.

\subsection{Range reasoning}
Patch supports ranged recipe parameters:

\begin{lstlisting}
make reward(player, bonus number 0..5):
  change player:
    add bonus * 2 to score
\end{lstlisting}

The production interval analyzer infers the change amount as $[0,10]$. A corresponding policy bound of 10 can therefore be accepted. Runtime guards enforce declared parameter bounds so the production execution cannot trivially violate the analyzer's input assumption.

The production interval analyzer is currently a small abstract interpretation over numeric literals, ranged variables, unary signs, parentheses, and basic arithmetic. Its semantic soundness is an open mechanization task. Beta 6 proves the soundness of the \emph{checker's interval-containment decision} once intervals have already been translated into the formal evidence; it does not yet prove that the production analyzer inferred those intervals correctly.

\section{Lean Semantics and Soundness}
The formal project is pinned to Lean 4.30.0 and contains three principal modules.

\paragraph{\texttt{PatchFormal.lean}.}
Defines values, semantic operations, changes, machine state, the single modeled change step, intervals, semantic effects, capability rules, and relational coverage judgments.

\paragraph{\texttt{PatchSignature.lean}.}
Defines a structured core
\begin{verbatim}
skip | emit effect | seq s1 s2 | branch s1 s2 | repeat n body
\end{verbatim}
with static \texttt{inferSignature} and a runtime \texttt{Executes stmt trace} relation.

\paragraph{\texttt{PatchChecker.lean}.}
Defines executable boolean checks over intervals, individual rule/effect pairs, policies, and protected statements, then proves those decisions sound with respect to the relational semantics.

\subsection{Change Signature Soundness}
For the structured core, Lean proves
\[
Executes(s,r) \Longrightarrow RuntimeChanges(r) \subseteq Sig(s).
\]
Branch inference includes effects from both alternatives; an actual execution chooses one. Thus the signature can over-approximate but cannot omit an emitted effect. Repetition may emit an effect multiple times, while the signature records the effect kind as covered.

\subsection{Capability containment}
Let $Cap(s)$ denote the semantic rules associated with a protected statement. If all inferred signature effects are admitted by policy, then Change Signature Soundness yields
\[
RuntimeChanges(s) \subseteq Sig(s) \subseteq Cap(s),
\]
and therefore
\[
RuntimeChanges(s) \subseteq Cap(s).
\]
The formal theorem \texttt{endToEndCapabilitySoundness} establishes this result for the modeled core.

\section{Verified Policy Checker}
Beta 6 replaces an important logical assumption at the artifact boundary with an executable checker whose soundness is itself proved.

For intervals, the checker computes
\[
withinBool(I,P)= (P.lo \le I.lo) \wedge (I.hi \le P.hi).
\]
Lean proves
\[
withinBool(I,P)=true \Longrightarrow Within(I,P).
\]

A rule/effect checker then compares target, field, operation kind, and amount policy. Its soundness theorem states
\[
allowsBool(rule,effect)=true \Longrightarrow Allows(rule,effect).
\]
Rule search and whole-signature checking are similarly lifted to a theorem
\[
policyAllowsBool(Sig,Policy)=true
\Longrightarrow PolicyAllows(Sig,Policy).
\]

Finally,
\[
checkProtected(s,P)=policyAllowsBool(inferSignature(s),P).
\]
Combining checker soundness with Change Signature Soundness gives the key beta-6 theorem:
\[
\begin{split}
&Executes(s,r) \wedge checkProtected(s,P)=true\\
&\qquad\Longrightarrow \forall e\in r.\;\exists p\in P.\;Allows(p,e).
\end{split}
\]
This theorem is implemented as \texttt{checkedExecutionCannotEscape}.

The important engineering consequence is that, for translated formal evidence, the JavaScript production policy checker is not the final authority. Lean recomputes the semantic policy decision using a much smaller checker.

\section{Production-to-Formal Validation and Certificates}
\subsection{Translation-validation bridge}
The production analyzer and the formal model are not simply assumed to agree. For an explicit subset, \texttt{src/formal-bridge.js} independently lowers the real production AST into a CoreStmt-like representation and derives a second formal-style signature:

\begin{verbatim}
production AST --------------------> production signature
      |
      v
independent bridge lowering
      |
      v
CoreStmt-like representation
      |
      v
formal-style signature
      |
      +----------------------------> compare
\end{verbatim}

A supported mismatch is a compiler error. Unsupported constructs are recorded explicitly rather than silently labeled verified. The current bridge covers direct supported semantic changes, sequence, branch alternatives, literal bounded repetition, and supported numeric intervals. Recipe calls, dynamic repetition, undo/redo, return control flow, and GUI/event execution remain outside this correspondence subset.

This architecture is related to translation validation \cite{necula2000translation}; Patch does not claim the technique itself as new.

\subsection{Generated certificates}
For a protected bridge-supported recipe, the production CLI can emit:

\begin{verbatim}
patch certify program.patch --out Program.patchcert.lean
\end{verbatim}

The generated Lean file contains:
\begin{itemize}[leftmargin=*]
\item a SHA-256 hash of the exact Patch source bytes;
\item the Patch IR version;
\item the translated formal statement;
\item the translated semantic policy;
\item a theorem that \texttt{checkProtected} evaluates to true, discharged by Lean computation; and
\item a runtime-safety theorem invoking \texttt{checkedExecutionCannotEscape}.
\end{itemize}

Formal CI generates such a certificate from the production compiler and compiles it against the pinned Lean checker. This resembles the producer/evidence/checker separation of Proof-Carrying Code \cite{necula1997pcc}; Patch does not claim proof-carrying evidence as new.

\subsection{Trusted computing base}
Beta 6 deliberately separates what is and is not currently established.

The following boundary remains trusted/unproved:
\begin{verbatim}
Patch source -> JavaScript parser -> bridge translation -> CoreStmt
\end{verbatim}

After that boundary, the policy judgment is Lean-checked:
\begin{verbatim}
CoreStmt + policy
  -> inferSignature
  -> verified policy checker
  -> PolicyAllows theorem
  -> runtime containment for formal Exec traces
\end{verbatim}

The source hash protects artifact identity, not translation correctness. A future source/Change-IR-to-CoreStmt correspondence theorem is therefore more valuable than adding further checker layers.

\section{Implementation and Artifact Status}
The beta-6 production path is:
\begin{verbatim}
Patch source
  -> parser / AST + range annotations
  -> production Change Signature analysis
  -> production Change Capability validation
  -> formal bridge validation
  -> Change IR 0.5
  -> Lean certificate             [implemented]
  -> .patchapp                    [implemented]
  -> bootstrap .wasm              [implemented]
  -> direct Wasm lowering         [next]
  -> native host packaging        [planned]
\end{verbatim}

The JavaScript test suite currently contains 57 tests. CI runs on Windows, macOS, and Linux with Node 22 and 24. It checks syntax, language behavior, semantic contracts, bridge behavior, certificate generation, examples, portable bundles, bootstrap Wasm, and the generated project website.

Formal CI now explicitly builds \texttt{PatchFormal}, \texttt{PatchSignature}, and \texttt{PatchChecker}, then compiles a production-generated certificate. This stronger beta-6 configuration exposed latent Lean 4.30 compatibility issues that the previous bare Lake invocation did not actually compile; those issues were repaired. The artifact therefore distinguishes historical CI configuration from the current explicit proof-build gate.

Patch Studio remains a browser-first PWA and project website. It exposes the editor, GUI preview, initial visual Designer, Change Contract view, Change IR, and normal program execution. Certificate generation currently requires the Node/Lean toolchain rather than running entirely inside the browser.

The current WebAssembly backend emits a valid instantiable module containing Patch source and Change IR for a Patch host. It is intentionally described as \emph{bootstrap Wasm}; direct Change-IR-to-Wasm execution is not yet implemented.

\section{Related Work and Novelty Boundary}
Patch sits in a crowded space and broad priority claims would be inappropriate.

\paragraph{First-class state and state transitions.}
Plaid makes abstract object-state changes first-class \cite{sunshine2011plaid}. Worlds reifies program state and supports scoped speculative side effects and commit/discard \cite{warth2011worlds}. Patch therefore does not claim to invent first-class state transition or reified state.

\paragraph{Effect and capability systems.}
Classical effect systems infer conservative effect approximations \cite{lucassen1988effects}. Effects as Capabilities relates effects and capability-based authority \cite{brachthaeuser2020effects}. Patch does not claim effect inference or effects-plus-capabilities as new. The candidate distinction is that operation- and magnitude-aware mutation effects are derived from the same semantic change representation through which persistent mutation must execute.

\paragraph{Translation validation and proof-carrying evidence.}
Translation validation checks properties of individual compiler results \cite{necula2000translation}. Proof-Carrying Code separates evidence generation from a smaller trusted verifier \cite{necula1997pcc}. Patch beta 6 uses related assurance ideas and claims no novelty for those architectures. Their role is to reduce trust in the production analyzer when evaluating Patch's semantic-contract hypothesis.

\paragraph{Change calculi and patch systems.}
Edit Lenses model explicit edits across related structures \cite{hofmann2012edit}; higher-order change structures support incremental computation \cite{cai2014changes}; formal patch theories study composition and commutation \cite{angiuli2016patch}. Patch borrows the general insight that changes deserve semantic structure.

\paragraph{Provenance and why debugging.}
Whyline demonstrates the utility of asking why and why-not questions about program behavior \cite{ko2008whyline}. Patch's current \texttt{why} facility is narrower and based on recorded semantic state transitions. It is supporting tooling rather than a primary novelty claim.

\paragraph{Educational representations.}
Scratch demonstrates the value of low-complexity representations and immediate feedback \cite{resnick2009scratch}. Patch's usability hypothesis is that a stronger mutation model need not force a more complicated beginner surface; this remains an empirical question rather than a demonstrated result.

\section{Evaluation Plan}
A high-venue submission requires evidence beyond the current artifact tests.

\paragraph{E1: Formal correspondence.}
Define and mechanize a correspondence relation between a useful production Change IR fragment and the Lean CoreStmt/effect vocabulary. The critical failure criterion is a production behavior not represented in the formal evidence while still being labeled certified.

\paragraph{E2: Interval-analysis soundness.}
Formalize the supported numeric expression language and prove that every concrete evaluation satisfying the input range environment lies inside the production-inferred interval.

\paragraph{E3: Semantic-security case studies.}
Build at least two or three applications in which operation- or magnitude-sensitive authority prevents concrete violations. Candidate cases include a reward plugin, bounded account debit, and game/UI extension. At least one case should lie entirely within the beta-6 certifiable subset.

\paragraph{E4: Conventional baselines.}
Compare Patch with conventional implementations that require explicit validation, logging, rollback, or command/event infrastructure. Measure annotations, application-specific security checks, change/audit plumbing, and defect-seeding outcomes rather than only source-line counts.

\paragraph{E5: Cost.}
Measure production analysis time, bridge time, certificate size/generation time, Lean checking time, runtime change-recording overhead, and later direct-Wasm performance.

\paragraph{E6: Usability, if retained.}
If the paper makes a substantive simplicity claim, preregister a controlled study comparing comprehension and modification tasks with conventional mutable syntax. Advanced formal/capability tasks should be separated from basic mutation-comprehension tasks.

\section{Limitations and Threats}
The formal core is intentionally smaller than the production language. Recipe calls, dynamic loops, GUI events, undo/redo, richer values, external I/O, and several mutation classes are not yet part of the certificate correspondence subset. The JavaScript source/AST-to-CoreStmt translation is not formally verified. Consequently, a beta-6 certificate establishes the policy theorem for the translated formal statement, not yet a source-level theorem for arbitrary Patch code.

The production interval analyzer is not yet mechanized against expression evaluation. Runtime range guards reduce one practical mismatch but do not replace a static soundness proof. The current production call analysis is conservative and incomplete. Whole before/after snapshots are inefficient for large structures. Provenance-based \texttt{why} is historical and does not establish counterfactual causation. Bootstrap Wasm is not direct executable lowering.

Novelty is also a threat. Behavioral types, refinement and quantitative effect systems, capability systems, state-transition languages, and domain-specific update calculi may contain closer precedents than currently identified. The submission must therefore make a precise technical claim and conduct a systematic prior-art review rather than rely on terminology such as ``change-oriented.''

Finally, the stronger beta-6 formal CI revealed that an earlier bare \texttt{lake build} invocation could report success without actually compiling the intended proof modules. The current artifact corrects that configuration by naming all proof targets explicitly and compiling a generated certificate. Claims in this manuscript refer to the current beta-6 gate.

\section{Conclusion}
Patch investigates a specific language factorization: persistent mutation is represented and executed as semantic change rather than ordinary assignment with change metadata reconstructed later. This mandatory mutation substrate supports operation- and magnitude-aware Change Signatures and Capabilities, while a small Lean model proves signature and policy containment for a structured core.

Beta 6 adds a more credible assurance boundary. A production bridge exposes the correspondence subset and checks signature agreement, while an executable Lean checker independently validates translated semantic-policy evidence. Production-generated certificates can therefore carry a machine-checked policy theorem without trusting the JavaScript production policy decision. The remaining source-to-formal translation gap is explicit and becomes the next principal formal target.

The project is not yet a top-venue submission. Its strongest path is now narrow: prove the remaining correspondence and interval-analysis obligations for a useful subset, demonstrate one or two compelling certified security cases, measure cost and engineering benefit, and keep the paper centered on mandatory semantic mutation plus quantitative semantic authority rather than the surrounding IDE or product features.
