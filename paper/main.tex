\title{Patch: State-Change Factorization and Semantic Change Contracts for Transparent Mutable Programs}
\author{Mich\'el Nguyen}
\date{August 2026}

\begin{document}
\maketitle

\begin{abstract}
General-purpose languages commonly expose persistent mutation through assignment or data-structure-specific updates, while auditing, undo, provenance, replay, and policy reconstruct semantics around those writes. Patch explores the opposite factorization: ordinary post-creation persistent mutation is committed through a structured semantic \emph{Change}, with no alternative modeled assignment route. We call this \emph{State-Change Factorization}.

Patch derives \emph{Semantic Change Signatures} and optional \emph{Change Capabilities} from the same representation. Contracts distinguish target, operation, and, for a supported numeric fragment, magnitude, allowing bounded increase authority without set or decrease authority. A Lean 4 development proves factorization, mutation transparency, signature/policy properties, integer range soundness, and finite exact call-tree refinement for explicit fragments.

Selected production direct-WebAssembly executions are linked to the formal model through independent validation and generated evidence. Beta 32 reconstructs invocation frames without trusting backend call markers, and Lean re-evaluates frame-selected effects before deriving caller-signature refinement. Capture, validator correctness, remaining parser semantics, lowering, and the WebAssembly engine remain trust boundaries.

Evaluation combines an eight-case semantic-authority ablation, two application cases, and a commit-bound mutation-shape stress test over 15 public state updates. The public projects are neither translated to nor executed by Patch; the test asks whether each mutation fits the current single-target Change abstraction and whether Patch would own the commit route. Twelve sites have a single-target set/add/remove shape; seven cross foreign host-state APIs and three bundle multiple targets. No performance, third-party execution, complete-sandboxing, or end-to-end compiler-verification claim is made.
\end{abstract}

\noindent\textbf{Keywords:} programming languages; mutation; effects; capabilities; verification; WebAssembly

\section{Introduction}
Mutable programs often need answers beyond the current value of a variable. Debuggers need provenance, interfaces need undo, replay systems need stable transition records, and security mechanisms need to constrain authority. Conventional languages commonly layer these services around writes whose semantic meaning is only partially represented by the language.

Patch asks what changes if the semantic update is primary. Instead of first mutating state and later attaching metadata, a Patch program describes a change that is itself the modeled route to a new persistent state:

\begin{lstlisting}
create number score = 0

change score:
  add 1
\end{lstlisting}

The same mutation vocabulary supports authority more precise than binary write permission:

\begin{lstlisting}
allow reward:
  score may increase up to 10

make reward(bonus number 0..5):
  change score:
    add bonus * 2
\end{lstlisting}

The policy authorizes a bounded increase. It does not authorize an arbitrary \texttt{set}, even though both operations write the same persistent location.

The research question is not whether first-class state change, effects, quantitative typing, capabilities, event-backed state, state-transition specifications, translation validation, or proof-carrying evidence exist. They do, and several related systems are more expressive than Patch along individual dimensions. The narrower hypothesis is architectural: ordinary modeled persistent mutation is factored through one semantic delta representation, and operation- and magnitude-aware summaries and authority are derived from that same mandatory route, so execution, contracts, history, provenance, and assurance share one mutation substrate.

\paragraph{Research questions.}
This paper evaluates four questions about that architecture:
\begin{enumerate}[leftmargin=*]
\item[\textbf{RQ1}] Can modeled persistent mutation be factored through one semantic Change route while retaining transparent history and derived semantic contracts?
\item[\textbf{RQ2}] Does operation- and magnitude-aware authority distinguish mutation cases that target-only write authority does not distinguish?
\item[\textbf{RQ3}] Can selected production direct-WebAssembly executions be related back to exact semantic call-tree effects without trusting backend call markers?
\item[\textbf{RQ4}] Do mutation shapes observed in public software fit the current single-target Patch Change abstraction, and which shapes or persistence routes fall outside it?
\end{enumerate}

\begin{claimboundary}
This manuscript does not claim unique expressibility of bounded state relations, a fully verified compiler, a complete plugin sandbox, third-party Patch execution, or any overhead/scalability result. RQ1 concerns the modeled mutation architecture, RQ2 its semantic-authority distinction, RQ3 a bounded production-to-formal assurance bridge, and RQ4 a qualitative representational stress test rather than compatibility, migration, or ecosystem-prevalence evidence.
\end{claimboundary}

\paragraph{Contributions.}
This manuscript makes four scoped contributions:
\begin{enumerate}[leftmargin=*]
\item State-Change Factorization and Mutation Transparency for the modeled persistent-mutation machine (Defs.~\ref{def:factorization} and~\ref{def:transparency}), together with Semantic Change Signatures and Change Capabilities derived from the same mandatory mutation substrate;
\item a Lean assurance stack proving signature/policy and integer \texttt{RangeExpr} soundness plus finite transitive exact call-tree refinement for explicit fragments (Thms.~\ref{thm:signature}, \ref{thm:range}, and~\ref{thm:calltree});
\item a production-to-formal bridge in which independent JavaScript validation and beta~32 invocation-frame reconstruction produce evidence that Lean checks for selected direct-WebAssembly executions, without claiming a verified parser, backend, or runtime (Thm.~\ref{thm:runtime});
\item evaluation through an eight-case semantic-authority ablation, two internally authored application domains, a commit-bound 15-site public-code mutation-shape stress test, and deterministic reproducibility packaging.
\end{enumerate}

\section{Language Design}
\subsection{Progressive disclosure}
A beginner can ignore signatures, policies, certificates, and backend details:

\begin{lstlisting}
create number lives = 3
change lives:
  remove 1
show lives
\end{lstlisting}

Advanced machinery derives information from the same source mutation model rather than requiring a second command/event architecture for ordinary persistent state updates.

\subsection{No persistent-assignment escape hatch}
\texttt{create} introduces a fresh persistent binding. Existing persistent bindings are not subsequently updated with ordinary \texttt{x = e}; state-changing source uses \texttt{change}. This syntactic restriction mirrors the single modeled commit route in the formal machine. Transient GUI event values, toolkit selection, and layout state are deliberately not persistent Patch state unless source executes an explicit semantic \texttt{change}.

\subsection{Source and semantic operations}
The source-facing verbs are \texttt{set}, \texttt{add}, \texttt{remove}, and \texttt{clear}. Static semantic analysis can classify numeric mutations more precisely: \texttt{add 5} is an increase, \texttt{add -5} is a decrease, and \texttt{set 5} remains a set. Policies can distinguish these authorities even when they address the same location.

\section{State-Change Factorization and Change Contracts}
Let persistent state be a map $\sigma : Name \rightarrow Value$, let $\nu(x)$ be the current version of target $x$, and let history be $H=[\delta_1,\ldots,\delta_n]$. A normalized semantic change is
\[
\delta = \langle x,b,n,v,\Delta,v'\rangle,
\]
where $x$ is the target, $b$ and $n$ are base and new versions, $v$ and $v'$ are before and after values, and $\Delta$ is an ordered sequence of semantic operations. Well-formedness requires
\[
applyOps(\Delta,v)=v' \quad\text{and}\quad n=b+1.
\]

\begin{definition}[State-Change Factorization]
\label{def:factorization}
For every state-changing step in the current Lean machine, there exists a well-formed $\delta$ such that the resulting machine is exactly the modeled commit of $\delta$.
\end{definition}

\begin{definition}[Mutation Transparency]
\label{def:transparency}
The witnessing change appears in resulting history.
\end{definition}

For a recipe $f$, a Change Signature conservatively describes semantic effects,
\[
Sig(f)=\{e_1,\ldots,e_k\}.
\]
An effect contains target, optional field, semantic operation kind, and optional amount interval. A Change Capability specifies admitted semantic authority. Thus \texttt{score may increase up to 10} distinguishes bounded increase from set or decrease authority on the same persistent location.

The novelty hypothesis is not that equivalent bounds are inexpressible in richer effect or refinement systems. It is that Patch derives this restricted authority vocabulary from the same mandatory semantic delta objects through which modeled persistent mutation is committed.

\section{Formal Assurance Stack}
The assurance argument has four layers: the semantic Change machine, static effect and range reasoning, finite exact recipe-call composition, and a bounded bridge from selected production direct-WebAssembly executions back to exact formal effects. The paper reports the proved statement at each layer and names what remains trusted rather than narrating the implementation history of every intermediate beta.

\subsection{Core semantic and static guarantees}
For the structured semantic core, Lean proves that executed changes are covered by the inferred Change Signature. If the inferred signature is admitted by policy, those changes are also admitted by the declared capability:
\[
RuntimeChanges(s) \subseteq Sig(s) \subseteq Cap(s).
\]

\begin{theorem}[Change Signature / Capability Soundness]
\label{thm:signature}
On the modeled \texttt{CoreStmt} fragment, every executed runtime change is covered by the inferred signature, and a successful policy check implies that those runtime changes are admitted by the declared capability.
\end{theorem}

Magnitude reasoning uses an explicit integer \texttt{RangeExpr} grammar. For a supported expression $e$,
\[
EnvRespects(\Gamma,\rho) \wedge analyzeRange(e,\Gamma)=I \wedge eval(e,\rho)=v
\Longrightarrow v\in I.
\]

\begin{theorem}[Integer range soundness]
\label{thm:range}
If the environment respects $\Gamma$ and range analysis returns interval $I$ for a supported integer \texttt{RangeExpr}, every concrete evaluation of that expression lies in $I$.
\end{theorem}

The mechanized range fragment contains integer literals, ranged variables, addition, subtraction, negation, and multiplication by a non-negative integer constant. Decimal/floating-point semantics, division, and general multiplication are outside this theorem.

Independent raw-source validators reconstruct supported range expressions, guards, and static call-site identity separately from the production path. Certification requires agreement before formal witnesses are accepted. This reduces selected extraction dependencies; it is translation validation, not a Lean proof of the JavaScript parsers or scanners.

\subsection{Finite exact recipe calls}
The call layer combines conservative recipe signatures with exact bindings for selected executions. Finite ranked call trees preserve nested argument bindings, supported guard choices, static repeats, and direct effects. Arithmetic expressions are retained for Lean re-evaluation rather than replaced by trusted JavaScript constants.

\begin{theorem}[Finite transitive call-tree refinement]
\label{thm:calltree}
For a selected finite exact call tree in the encoded fragment, \texttt{checkedConcreteTransitiveCallTreeRefinesCallerSignature} establishes that the selected exact trace is covered by the caller semantic signature.
\end{theorem}

The theorem is intentionally finite and fragment-scoped. Unsupported state-dependent guards, out-of-fragment expressions, or call structures fail closed rather than being silently treated as verified.

\subsection{Production direct-WebAssembly correspondence}
The production direct backend lowers a conservative numeric Console subset to WebAssembly. Runtime capture exposes target/before/after transitions. An independent Change-IR executor reconstructs expected transitions and semantic effect occurrences rather than trusting backend semantic annotations.

Beta~32 additionally reconstructs invocation frames without trusting backend call-entry/exit markers. A frame records caller/callee identity, dynamic invocation ordinal, parent/depth information, exact arguments/bindings, and transition boundaries. For an accepted witness, the reconstructed frame binding must equal the exact formal callee binding. Lean then re-evaluates the frame-selected observed effects against the exact call-tree statement before deriving caller-signature refinement.

The strongest regression executes \texttt{caller(1)}, \texttt{caller(4)}, and \texttt{caller(1)} through a four-frame call chain. Independent validation reconstructs twelve invocation frames and six transitive correspondences. The repeated first and third roots remain distinct dynamic invocations, while the middle root selects the opposite supported guard path. This directly tests the ambiguity that a globally scoped effect list would leave unresolved.

\begin{theorem}[Observed runtime-frame correspondence]
\label{thm:runtime}
Given accepted independently reconstructed invocation-frame evidence whose bindings equal the exact formal callee bindings, Lean re-evaluates the frame-selected observed effects and, when they match the exact call-tree statement, derives caller-signature refinement via \texttt{checkedObservedTransitiveRuntimeRefinesCallerSignature}.
\end{theorem}

This theorem proves a consequence of accepted evidence. It does not prove that every faulty execution would necessarily be captured or reconstructed correctly.

\subsection{Exact trust boundary}
The current assurance stack is not an end-to-end compiler refinement theorem. Runtime transition capture, the independent JavaScript validator and frame reconstruction, parser/extractor behavior outside independently cross-checked fragments, JavaScript-to-WebAssembly lowering, and the WebAssembly engine remain outside the Lean proof.

\subsection{Answers to the research questions}
The evidence above supports four deliberately scoped answers.

\paragraph{RQ1: supported for the modeled fragment.}
The semantic machine factors each modeled state-changing step through a well-formed Change and records the witnessing Change in history. Change Signatures and optional Change Capabilities are derived from that same route. This establishes the architectural conjunction for the formal fragment, not for arbitrary foreign state or every product feature.

\paragraph{RQ2: yes for the evaluated authority dimensions.}
Operation and magnitude distinguish cases that the target-only ablation cannot distinguish. Four of eight micro-cases are rejected by Patch while the coarse write-target analysis accepts them, and the two application domains reproduce magnitude and direction distinctions through the production path. The result is evidence for semantic authority precision, not a universal comparison with richer prior systems.

\paragraph{RQ3: yes for selected certified direct-WebAssembly executions.}
Independent transition/effect validation and beta~32 frame reconstruction relate selected direct-WebAssembly observations to exact finite formal call-tree effects without trusting backend call markers. Repeated identical invocations and mixed supported guard paths are distinguished. The conclusion remains conditional on accepted evidence and does not imply a verified compiler or runtime.

\paragraph{RQ4: partial representational fit with explicit boundaries.}
In the frozen 15-site public-code stress test, twelve sites have a compact single-target set/add/remove shape. However, seven cross foreign host persistence APIs and three bundle multiple related targets. The result therefore supports the plausibility of the single-target Change abstraction while simultaneously identifying commit-route ownership and multi-target atomicity as boundaries of Paper~1.

Taken together, the evaluation answers the architectural, authority, runtime-correspondence, and representational questions separately. This separation is intentional: evidence for one question is not reused to imply stronger claims about another.

\section{Reproducibility and Artifact Boundary}
The \emph{Patch Reproducibility Bundle} binds the research artifact to an exact Patch version and 40-character source commit. CI regenerates the finite transitive call-tree certificate, direct-WebAssembly runtime certificates, repeated-call and mixed-guard frame certificates, semantic-authority report, and both application reports. Tracked source and regenerated evidence are packaged with SHA-256 identities in a deterministic archive.

The repository also contains process-isolated timing infrastructure, but Paper~1 makes no overhead or scalability claim. Hosted-CI timing is therefore regression data, not performance evidence; controlled timing becomes relevant only if a later manuscript revision introduces a performance claim.

Patch 0.2.0-beta.35 includes Patch Studio, source-backed Window tooling, native/portable deployment paths, richer GUI controls, and data types beyond the beta~32 formal fragment. These product capabilities are useful artifact surfaces but are not contributions evaluated by RQ1--RQ4 and do not widen the runtime-correspondence theorem. Transient toolkit/event state becomes modeled persistent Patch state only through an explicit semantic \texttt{change}.

\section{Limitations and Threats to Validity}
\label{sec:limitations}

\paragraph{Construct validity.}
The Lean theorems cover explicit fragments rather than the full language. Independent source/range, guard, and call-site validators reduce selected extraction trust, but they are JavaScript rather than verified parsers. Runtime correspondence checks consequences of accepted reconstructed evidence; it does not prove capture completeness, lowering correctness, or WebAssembly-engine correctness. The coarse security baseline is an internal target-only ablation, not a model of a named prior system.

\paragraph{Internal validity.}
Semantic-authority cases are deterministic artifact cases with expected accept/reject matrices rather than samples from a vulnerability corpus. The public-code mutation-shape stress test uses frozen source anchors and explicit classifications, but classification remains a manual research judgement. No controlled paper-quality timing dataset has been collected; because no performance claim is made, hosted-CI timing is retained only as regression and reproducibility evidence.

\paragraph{External validity.}
Checkout/loyalty and usage/quota are internally authored engineering cases. The 15-site public-code stress test uses purposeful diversity sampling rather than random or exhaustive repository mining. Its counts are descriptive of the frozen corpus only. The public projects are not translated to or executed by Patch, so the study does not establish source compatibility, migration feasibility, third-party Patch execution, certified adapters, atomic multi-target semantics, usability, or ecosystem prevalence. Seven sites cross foreign host-backed state APIs and three group multiple related targets; these are architectural boundaries, not failed or successful integrations. GUI, Things, native Window runtimes, and foreign code remain outside the beta~32 Lean fragment. The related-work review is structured but not claimed to be exhaustive.

The most valuable follow-on evidence is a genuine external integration or migration study, a broader systematic mutation corpus if prevalence claims are desired, and controlled performance measurements only if the paper later makes an overhead or scalability claim. Reducing remaining lowering/runtime and out-of-fragment parser trust would further strengthen assurance. Relational multi-target ChangeSets, certified host adapters, least-authority inference, temporal authority, causal debugging, and safe parallelism remain separate research questions rather than missing Paper~1 contributions.

\section{Conclusion}
Patch investigates a language architecture in which ordinary modeled persistent mutation is committed through an explicit semantic Change rather than merely observed after the fact. The same substrate supports operation- and magnitude-aware contracts, history, provenance, and a layered assurance argument while keeping beginner-facing mutation syntax compact.

The formal evidence establishes factorization, semantic-authority soundness properties, integer range soundness, finite exact call-tree refinement, and runtime-frame correspondence for explicit fragments. The production bridge is deliberately bounded: independent validators and frame reconstruction reduce selected trust dependencies, while capture, remaining parser semantics, lowering, validator correctness, and the WebAssembly engine remain named trust assumptions.

The evaluation then tests different consequences of the architecture rather than treating one result as evidence for everything. Semantic operation and magnitude reject four cases admitted by the target-only ablation; two larger domains reproduce the distinction through the production path; and the public-code stress test finds both compact single-target mutation shapes and concrete boundaries involving foreign persistence and multi-target grouping.

Paper~1 therefore argues for a specific architectural conjunction, not for firstness of any individual mechanism: modeled persistent mutation is committed through a structured semantic Change, and operation- and magnitude-aware summaries and authority are derived from that same mandatory route. Later work can address multi-target atomicity, host adapters, least-authority inference, and broader external evaluation without enlarging the contribution claimed here.
