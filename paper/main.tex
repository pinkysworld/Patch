\title{Patch: State-Change Factorization and Semantic Change Contracts for Transparent Mutable Programs}
\author{Mich\'el Nguyen}
\date{}

\begin{document}
\maketitle

\begin{abstract}
Mutable programs routinely need more information about state updates than a final value: debuggers need provenance, interfaces need undo, replay needs stable transitions, and security mechanisms need to constrain authority. Conventional languages usually expose persistent mutation through assignment or data-structure-specific update operations and reconstruct this additional semantic structure around those writes. Patch explores the opposite factorization. Ordinary post-creation persistent mutation is represented and committed through a structured semantic \emph{Change}; ordinary reassignment is not a second modeled persistent-update route. We call this property \emph{State-Change Factorization}.

From the same mandatory change representation, Patch derives \emph{Semantic Change Signatures} and optional \emph{Change Capabilities}. These contracts distinguish the changed target, semantic operation, and---for a supported numeric fragment---magnitude. A component can therefore be authorized to increase a target by at most a bound without receiving authority to set or decrease that target. A Lean 4 development establishes factorization, mutation transparency, signature and policy soundness, integer-range soundness, finite ranked call composition, exact call binding, guarded structured traces, and finite transitive call-tree refinement for explicit fragments.

The implementation connects a production direct-WebAssembly path to the formal model through independent validation and generated Lean-checkable evidence. Concrete invocation frames are reconstructed without trusting backend call markers, including repeated identical calls and calls that select different guard paths. The evaluation contains eight semantic-authority micro-cases and two larger application cases. In four micro-cases, a target-only write-authority ablation admits an extension that Patch rejects because of operation, magnitude, transitive magnitude, or unproved-magnitude authority; both approaches reject the target-escape case. Safe checkout/loyalty and usage/quota applications execute on the direct-WebAssembly path while controlled authority escalations are rejected.

Patch does not claim that bounded state relations, quantitative effects, capabilities, first-class state changes, or general state specifications are uniquely expressible. Its contribution is the narrower architecture in which execution, semantic authority, history, provenance, and assurance reuse the same mandatory persistent-mutation representation. The implementation is not an end-to-end verified compiler; runtime capture, validator correctness, unsupported parser fragments, lowering, and the WebAssembly engine remain explicit trust boundaries.
\end{abstract}

\noindent\textbf{Keywords:} programming languages; state mutation; effect systems; capabilities; formal verification; WebAssembly; provenance

\section{Introduction}
Mutable state is compact to program with but semantically expensive to recover after the fact. A write such as \texttt{x = e} identifies a destination and a value, yet many downstream tools need richer questions answered: Was the update an increase, decrease, replacement, or clear operation? By how much could it change the target? Which procedure was responsible? Was that authority intended? Which transition should be undone or explained?

Patch investigates whether these questions become simpler when the state transition itself is the primary abstraction. Instead of first mutating persistent state and later attaching metadata, a Patch program describes a structured semantic change that is the modeled route to the new persistent state:

\begin{lstlisting}
create number score = 0

change score:
  add 1
\end{lstlisting}

The same mutation vocabulary supports authority more precise than binary write permission:

\begin{lstlisting}
allow reward:
  score may increase up to 10

make reward(bonus number 0..5):
  change score:
    add bonus * 2
\end{lstlisting}

The policy authorizes a bounded increase. It does not authorize an arbitrary \texttt{set} or a decrease, even though all three operations would write the same persistent location.

The research question is deliberately narrower than the existence of first-class state change, effect systems, capabilities, quantitative typing, refinement specifications, translation validation, or proof-carrying evidence. Those mechanisms have substantial prior art, and several related systems are more expressive than Patch along individual dimensions. We ask whether forcing ordinary modeled persistent mutation through one semantic delta representation yields a useful architecture in which execution, operation/magnitude-aware authority, history, provenance, and assurance reuse the same substrate.

\paragraph{Research questions.}
The paper evaluates four questions:
\begin{enumerate}[leftmargin=*]
\item \textbf{RQ1---Factorization:} can ordinary post-creation persistent mutation be represented through a single semantic Change abstraction without a parallel assignment escape hatch in the modeled language?
\item \textbf{RQ2---Authority:} can operation- and magnitude-aware authority be derived from that same representation and reject behaviors that target-only write authority cannot distinguish?
\item \textbf{RQ3---Assurance:} which properties of the change model, signatures, capabilities, ranges, and finite interprocedural calls can be machine-checked for explicit fragments?
\item \textbf{RQ4---Implementation correspondence:} how far can a production direct-WebAssembly execution path be connected to those formal fragments while keeping the remaining trust boundary explicit?
\end{enumerate}

\begin{claimboundary}
The paper does not claim unique expressibility of bounded state relations, a fully verified compiler, a complete plugin sandbox, complete foreign-code confinement, or superiority over general effect/refinement/capability systems. The contribution hypothesis is architectural: modeled persistent mutation is factored through semantic Changes, and multiple analyses and tools reuse that mandatory representation.
\end{claimboundary}

\paragraph{Contributions.}
This paper makes five scoped contributions:
\begin{enumerate}[leftmargin=*]
\item \emph{State-Change Factorization} and \emph{Mutation Transparency}, a mutation architecture in which modeled post-creation persistent updates commit through structured semantic Changes (Defs.~\ref{def:factorization} and~\ref{def:transparency});
\item Semantic Change Signatures and Change Capabilities derived from the same mutation substrate, including operation- and magnitude-sensitive authority, with Lean-checked signature/policy and integer-range results for explicit fragments (Thms.~\ref{thm:signature} and~\ref{thm:range});
\item a layered finite-call assurance stack covering ranked composition, exact bindings, guard-selected traces, and finite transitive call-tree refinement (Thm.~\ref{thm:calltree});
\item an implementation bridge from production direct-WebAssembly execution to independently reconstructed semantic effects and invocation frames, with generated Lean-checkable evidence and an explicit non-verified trust boundary (Thm.~\ref{thm:runtime});
\item an artifact evaluation comprising eight semantic-authority micro-cases and two larger application domains, demonstrating distinctions unavailable to an intentionally coarse target-only write-authority ablation.
\end{enumerate}

\section{Language Design}
\subsection{Progressive disclosure}
A beginner can ignore signatures, policies, certificates, and backend details:

\begin{lstlisting}
create number lives = 3
change lives:
  remove 1
show lives
\end{lstlisting}

Advanced machinery derives information from the same source mutation model rather than requiring a second command/event architecture for ordinary persistent state updates.

\subsection{No persistent-assignment escape hatch}
\texttt{create} introduces a fresh persistent binding. Existing persistent bindings are not subsequently updated with ordinary \texttt{x = e}; state-changing source uses \texttt{change}. This syntactic restriction mirrors the single modeled commit route in the formal machine. Transient GUI event values, toolkit selection, and layout state are deliberately not persistent Patch state unless source executes an explicit semantic \texttt{change}.

\subsection{Source and semantic operations}
The source-facing verbs are \texttt{set}, \texttt{add}, \texttt{remove}, and \texttt{clear}. Static semantic analysis can classify numeric mutations more precisely: \texttt{add 5} is an increase, \texttt{add -5} is a decrease, and \texttt{set 5} remains a set. Policies can distinguish these authorities even when they address the same location.

\section{State-Change Factorization and Change Contracts}
Let persistent state be a map $\sigma : Name \rightarrow Value$, let $\nu(x)$ be the current version of target $x$, and let history be $H=[\delta_1,\ldots,\delta_n]$. A normalized semantic change is
\[
\delta = \langle x,b,n,v,\Delta,v'\rangle,
\]
where $x$ is the target, $b$ and $n$ are base and new versions, $v$ and $v'$ are before and after values, and $\Delta$ is an ordered sequence of semantic operations. Well-formedness requires
\[
applyOps(\Delta,v)=v' \quad\text{and}\quad n=b+1.
\]

\begin{definition}[State-Change Factorization]
\label{def:factorization}
For every state-changing step in the current Lean machine, there exists a well-formed $\delta$ such that the resulting machine is exactly the modeled commit of $\delta$.
\end{definition}

\begin{definition}[Mutation Transparency]
\label{def:transparency}
The witnessing change appears in resulting history.
\end{definition}

For a recipe $f$, a Change Signature conservatively describes semantic effects:
\[
Sig(f)=\{e_1,\ldots,e_k\}.
\]
An effect contains target, optional field, semantic operation kind, and optional amount interval. A Change Capability specifies allowed semantic authority. For example, \texttt{score may increase up to 10} distinguishes bounded increase from set or decrease authority.

The novelty hypothesis is not that an equivalent bound is inexpressible in richer effect or refinement systems. It is that Patch derives this restricted authority vocabulary from the same mandatory semantic delta objects through which modeled persistent mutation is committed.

\section{Formal Assurance Stack}
The artifact contains layered Lean modules for semantic changes, signatures, policy checking, source/range evidence, guard validation, abstract calls, exact call binding, structured callee traces, finite transitive call trees, and runtime-call correspondence.

\subsection{Signature and capability soundness}
For the structured semantic core, Lean proves a signature property of the form
\[
Executes(s,r) \Longrightarrow RuntimeChanges(r) \subseteq Sig(s).
\]
If every inferred effect is admitted by policy,
\[
RuntimeChanges(s) \subseteq Sig(s) \subseteq Cap(s).
\]

\begin{theorem}[Change Signature / Capability Soundness]
\label{thm:signature}
On the modeled \texttt{CoreStmt} fragment, every executed runtime change is covered by the inferred signature, and a successful policy check implies that those runtime changes are admitted by the declared capability.
\end{theorem}

The executable policy checker is proved sound with respect to the relational policy semantics for the modeled fragment.

\subsection{Integer range soundness}
For the explicit integer \texttt{RangeExpr} grammar, Lean proves schematically:
\[
EnvRespects(\Gamma,\rho) \wedge analyzeRange(e,\Gamma)=I \wedge eval(e,\rho)=v
\Longrightarrow v\in I.
\]

\begin{theorem}[Integer range soundness]
\label{thm:range}
If the environment respects $\Gamma$ and range analysis returns interval $I$ for a supported integer \texttt{RangeExpr}, every concrete evaluation of that expression lies in $I$.
\end{theorem}

The mechanized fragment includes integer literals, ranged variables, addition, subtraction, negation, and multiplication by a non-negative integer constant. Decimal/floating-point semantics, division, and general multiplication are not silently included in this theorem.

\subsection{Source, guard, and static call-site validation}
The production source path and independent raw-source paths reconstruct supported formal source/range and guard artifacts separately. Protected certification requires agreement for those supported fragments. Numeric range expressions and guards use independent validator-side parsers rather than reusing the corresponding production expression parser.

Concrete call certification also checks static source identity before trusting the production AST's call-site description. An independent raw-source scanner reconstructs each supported \texttt{do recipe(args)} site's caller recipe, callee, source line, order, and exact trimmed argument texts. That ordered list must match a separately collected production-AST list before concrete-call witnesses are accepted. Call-site evidence is then propagated through the structured, transitive, and runtime witness layers.

This is translation/source-identity validation, not a Lean proof of either JavaScript parser or scanner. Lean separately checks supported argument semantics after source identity is accepted.

\section{Finite Exact Recipe Calls}
\subsection{Abstract and exact call composition}
\texttt{PatchCalls.lean} models finite recipe environments with parameter intervals, semantic signatures, and well-founded ranks. The executable checker validates direct-effect membership, positional argument-interval fit, lower-rank call resolution, and callee-to-caller signature containment. For modeled rank-decreasing executions, \texttt{callSignatureSoundness} establishes caller-signature coverage.

Concrete evidence serializes exact bindings as name/integer pairs. \texttt{PatchCallSubstitution.lean} re-evaluates call arguments under an exact caller environment and checks positional binding. \texttt{PatchCallRefinement.lean} connects exact values through abstract argument intervals to declared parameter intervals, while \texttt{PatchCallEffect.lean} re-evaluates direct quantitative effects under the exact environment.

\subsection{Structured and guard-selected callee traces}
The structured exact-trace layer covers sequence and literal/static repetition and adds exact guard selection when guards depend only on supported recipe-parameter expressions. Unsupported state-dependent or out-of-fragment guards fail closed rather than being approximated as verified.

\subsection{Finite transitive exact call trees}
\texttt{PatchCallTree.lean} represents a finite selected call tree with exact nested bindings, direct effects, supported guard choices, static repeats, and strict rank decrease. Each nested edge imports the callee semantic signature into its caller.

The principal checked composition is exposed through
\begin{verbatim}
checkedConcreteTransitiveCallTreeRefinesCallerSignature
\end{verbatim}
which establishes that the selected finite exact trace is represented by the caller semantic signature, subject to the encoded fragment and executable checks.

\begin{theorem}[Finite transitive call-tree refinement]
\label{thm:calltree}
For a selected finite exact call tree in the encoded fragment, \texttt{checkedConcreteTransitiveCallTreeRefinesCallerSignature} establishes that the selected exact trace is covered by the caller semantic signature.
\end{theorem}

A representative source shape is:
\begin{lstlisting}
create number score = 0

make leaf(amount number 1..6):
  change score:
    add amount * 2

make middle(value number 0..5):
  do leaf(value + 1)

make caller(bonus number 0..5):
  do middle(bonus)

do caller(2)
\end{lstlisting}

The certificate preserves arithmetic expressions and nested bindings for Lean re-evaluation instead of trusting precomputed JavaScript constants.

\section{Direct-WebAssembly Runtime Correspondence}
\subsection{Independent transition and effect validation}
The production direct backend lowers a conservative numeric Console subset to WebAssembly. Runtime capture exposes target/before/after transitions. An independent Change-IR executor reconstructs expected transitions and semantic effect occurrences rather than trusting semantic call/effect annotations emitted by the backend.

The validator checks complete transition order and values, reconstructs lexical change sites and recipe scope, and checks observed semantic effects against production Change Signatures and, where applicable, Change Capabilities. Tampered transitions, signatures, and policies are regression-tested to fail closed.

\subsection{Call-aware bridge}
The implementation combines the exact finite call-tree witness with real direct-WebAssembly execution. Observed semantic effects are validated independently and compared with the selected formal call-tree trace. This narrows the gap between exact call semantics and compiled execution without turning the JavaScript validator or WebAssembly engine into proved components.

\subsection{Invocation-frame reconstruction}
A globally scoped effect list is insufficient when the same recipe is invoked repeatedly with identical arguments. The runtime-correspondence layer therefore reconstructs concrete invocation frames independently of backend call-entry/exit markers. Each frame records caller/callee identity, dynamic invocation ordinal, parent/depth information, exact arguments/bindings, and transition boundaries. Validated effects carry the active frame stack.

For every selected exact call-tree witness, generated evidence checks that the reconstructed frame binding equals the exact formal callee binding:
\begin{verbatim}
runtimeFrameBindings = exactCallTreeBindings
\end{verbatim}
Lean then re-evaluates the frame-selected observed effects against the exact call-tree statement through \texttt{evalCallTreeStmtEqBool} before applying
\begin{verbatim}
checkedObservedTransitiveRuntimeRefinesCallerSignature
\end{verbatim}
to conclude caller-signature refinement for the accepted observed list.

The regression source \texttt{examples/formal-transitive-calls-repeated.patch} executes two identical root calls. Independent reconstruction assigns distinct dynamic frames, so their effects can be attributed and checked separately without trusted backend call markers.

A stronger regression, \texttt{examples/formal-transitive-calls-mixed-guards.patch}, executes \texttt{caller(1)}, \texttt{caller(4)}, and \texttt{caller(1)} through a four-frame call chain. The first and third invocations are identical and select the same guard branch, while the middle invocation selects the opposite branch. Independent validation reconstructs twelve invocation frames and six supported transitive correspondences. The three \texttt{caller -> outer} witnesses carry distinct dynamic frame identities and bindings 1, 4, and 1, while their selected effects are respectively \texttt{coins +4}, \texttt{score +5}, and \texttt{coins +4}. Lean re-checks each selected trace against its exact call-tree witness.

\begin{lstlisting}
create number score = 0
create number coins = 0

make leaf(amount number 1..5):
  if amount >= 3:
    change score:
      add amount
  else:
    change coins:
      add amount * 2

make middle(seed number 0..4):
  do leaf(seed + 1)

make outer(seed number 0..4):
  do middle(seed)

make caller(seed number 0..4):
  do outer(seed)

do caller(1)
do caller(4)
do caller(1)
\end{lstlisting}

\begin{theorem}[Observed runtime-frame correspondence]
\label{thm:runtime}
Given accepted independently reconstructed invocation-frame evidence whose bindings equal the exact formal callee bindings, Lean re-evaluates the frame-selected observed effects and, if they match the exact call-tree statement, derives caller-signature refinement via \texttt{checkedObservedTransitiveRuntimeRefinesCallerSignature}.
\end{theorem}

This is a consequence of accepted evidence, not a proof that every faulty trace would be captured.

\subsection{Exact trust boundary}
The runtime bridge is not an end-to-end compiler refinement theorem. The following remain outside the current Lean proof:
\begin{itemize}[leftmargin=*]
\item correctness and completeness of runtime transition capture;
\item correctness and completeness of the independent JavaScript transition/effect validator and invocation-frame reconstruction;
\item production parser/extractor correctness outside independently cross-checked supported source/range, guard, and static call-site identity fragments;
\item correctness of the independent JavaScript source/range, guard, and call-site validators themselves;
\item JavaScript-to-WebAssembly lowering correctness;
\item WebAssembly-engine correctness.
\end{itemize}

The certificate establishes consequences of accepted, independently reconstructed evidence for the formal fragment. The raw-source call-site check reduces one dependency on production-AST source identity, but it does not prove the production parser correct or validate arbitrary expression semantics. The runtime evidence likewise does not prove that every possible faulty trace would necessarily be captured or reconstructed correctly.

\section{Semantic-Authority Evaluation}
\subsection{Evaluation design}
The evaluation asks a deliberately narrow question: does operation/magnitude-aware authority derived from the mandatory Change representation distinguish behaviors that a target-only write-authority abstraction does not? The artifact contains eight extension-style micro-cases. Each case is evaluated by the real Patch compiler/Change Capability analysis and by an intentionally coarse internal ablation that records only transitively reachable changed target paths. The coarse baseline deliberately ignores semantic operation, magnitude, and proof obligations. It is not intended as a model of any named prior effect or capability system.

\subsection{Checkout/loyalty application}
A larger case study models a checkout extension that composes discount and loyalty helpers over multiple state paths. The safe variant executes through the real direct-WebAssembly path and terminates with
\[
balance=80,\qquad points=8,\qquad cashback=0.
\]
Its protected entry signature includes the transitive balance-decrease and points-increase effects with the expected bounds.

Controlled variants escalate reward magnitude, reverse the balance operation direction, or target unauthorized cashback state. Patch rejects these violations according to Semantic Change Contracts; the first two remain intentionally invisible to the internal target-only ablation, while the target escape is rejected by both.

\subsection{Usage/quota application}
A second application case changes domain rather than adding another checkout mutation. It models bounded usage accounting over \texttt{used}, \texttt{remaining}, \texttt{bonus}, and an unauthorized \texttt{admin\_credit} path. The safe variant executes through the same production direct-WebAssembly path and terminates with
\[
used=35,\qquad remaining=85,\qquad bonus=5,\qquad admin\_credit=0.
\]
The protected entry signature contains transitive usage-increase, quota-decrease, and bonus-increase effects with their declared bounds. Controlled variants exercise magnitude escalation, operation-direction reversal, and target escape under the same internal target-only ablation.

\paragraph{Answer to RQ2.}
Within these controlled cases, the mandatory semantic-change representation exposes authority dimensions that a target-only write abstraction intentionally discards. The result is not that Patch can express policies unavailable to richer systems; it is that operation and bounded magnitude are available directly from the mutation representation and can be checked without a separate general-purpose specification for these cases.

\section{Implementation and Reproducibility Artifact}
The research artifact is implemented in the Patch language/compiler repository. The paper's formal/runtime correspondence covers a conservative numeric Console subset. The broader product artifact also contains a browser-first Patch Studio, source-backed Window tooling, portable C99 and native packaging paths; these improve inspectability and experimentation but are not primary novelty claims and do not widen the Lean theorem.

Patch Studio exposes the practical consequences of the same mutation representation through history, undo/redo, provenance-oriented inspection, Change Signatures, and capability diagnostics. GUI toolkit state, Things, native Window runtimes, and foreign code remain outside the formal runtime-correspondence fragment unless Patch source explicitly commits a supported semantic Change.

The \emph{Patch Reproducibility Bundle} binds research evidence to an exact Patch version and source commit. CI regenerates the finite transitive call-tree certificate, direct-WebAssembly runtime certificate, repeated-call and mixed-guard invocation-frame certificates, semantic-authority report, and both application reports. The bundle records byte size and SHA-256 for included source/evidence files and creates a deterministic archive envelope. Performance timing is deliberately excluded from this reproducibility claim because hosted runner hardware is heterogeneous.

The repository also contains a process-isolated fixed-machine measurement protocol for future assurance-cost experiments. No controlled paper-quality timing dataset is used in this paper, and therefore no overhead, scalability, or asymptotic-performance claim is made.

\section{Limitations and Threats to Validity}
\label{sec:limitations}

\paragraph{Construct validity.}
The Lean theorems cover explicit fragments rather than the full language. Independent source/range, guard, and call-site validators reduce selected extraction trust, but they are JavaScript rather than verified parsers. Runtime correspondence checks consequences of accepted reconstructed evidence; it does not prove capture completeness, lowering correctness, or WebAssembly-engine correctness. The coarse security baseline is an internal target-only ablation, not a model of a named prior system.

\paragraph{Internal validity.}
The semantic-authority cases are deterministic artifact cases with predeclared accept/reject expectations rather than samples from a vulnerability corpus. Their role is to isolate semantic authority dimensions, not to estimate real-world vulnerability prevalence or prevention rates. The implementation contains tests for tampered transitions, signatures, and policies, but those tests are not a proof of validator completeness.

\paragraph{External validity.}
Checkout/loyalty and usage/quota are internally authored engineering cases, not third-party extensions and not evidence about an external plugin ecosystem. GUI, Things, native Window runtimes, foreign code, and unsupported numeric operations remain outside the formal correspondence fragment. A future external integration study would materially strengthen the practical generality claim.

\paragraph{Performance validity.}
No fixed-machine controlled timing dataset is reported. The paper therefore makes no claim that the assurance pipeline is cheap, linear, or suitable for a particular latency budget. The repository's process-isolated measurement protocol is provided to make such a study reproducible rather than to substitute methodology for results.

\paragraph{Novelty boundary.}
The related-work comparison is architectural rather than an expressiveness ordering. A richer effect, refinement, typestate, or dependent system may encode policies equal to or stronger than Patch's bounded semantic changes. The proposed contribution is the reuse of a mandatory mutation representation across execution, authority, history, provenance, and assurance; whether that architectural restriction is worthwhile beyond the evaluated cases remains an empirical and design question.

\section{Conclusion}
Patch investigates a language architecture in which ordinary modeled persistent mutation is not merely observed but factored through an explicit semantic Change representation. The same substrate supports operation- and magnitude-aware contracts, history, provenance, and assurance while keeping beginner-facing mutation syntax compact.

For RQ1 and RQ3, the formal model and Lean development establish State-Change Factorization, Mutation Transparency, signature/policy soundness, integer-range soundness, guarded structured-trace reasoning, and finite transitive call-tree refinement for explicit fragments. For RQ4, independently reconstructed runtime evidence connects selected production direct-WebAssembly executions to exact call-tree witnesses while keeping capture, validator, parser, lowering, and engine correctness outside the theorem.

For RQ2, the semantic-authority evaluation shows four controlled cases in which target-only write authority admits an extension that Patch rejects because of semantic operation, magnitude, transitive magnitude, or unproved magnitude, while both reject an unauthorized target escape. Two larger application domains exercise the same distinctions on the production direct-WebAssembly path. These results support the narrower architectural claim without asserting unique expressibility or complete sandboxing.

The next empirical step is external application evidence and controlled assurance-cost measurement. Neither is required to state the current formal and semantic-authority results, but both would test whether the additional semantic structure justifies its implementation and programming cost in broader settings.
