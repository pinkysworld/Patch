\title{Patch: State-Change Factorization and Semantic Change Contracts for Transparent Mutable Programs}
\author{Mich\'el Nguyen}
\date{Beta artifact manuscript, August 2026}

\begin{abstract}
Programming languages normally expose mutation through assignment or data-structure-specific operations, while tools later reconstruct why state changed for debugging, undo, replay, auditing, or policy enforcement. Patch explores a different factorization. Post-creation persistent mutation is compiled into and executed through a normalized semantic change representation. A programmer writes \texttt{change score: add 1}; the compiler/runtime constructs a structured delta that identifies the target, semantic operation, version transition, before/after values, and inverse information where supported. We call the central property \emph{State-Change Factorization}: every supported persistent transition from $S$ to $S'$ occurs through a semantic change $\delta$ satisfying $apply(\delta,S)=S'$, with no ordinary persistent-assignment escape hatch.

Patch 0.2 beta.4 builds analysis and tooling layers on the same representation. \emph{Semantic Change Signatures} describe semantic changes a component may commit, while optional \emph{Change Capabilities} constrain allowed targets, operation kinds, and numeric magnitudes. Bounded numeric recipe parameters support interval reasoning, so a dynamic expression such as \texttt{bonus * 2} can be proved to remain inside a capability bound. Committed changes also retain source, recipe, and GUI-event provenance, enabling an initial \texttt{why} facility for explaining values and the first recorded transition that made a condition true.

The formal contribution is strengthened in beta.4. A Lean 4 model mechanizes State-Change Factorization, Mutation Transparency, interval-containment transitivity, and a structured control-flow core with static Change Signature inference. For that formal core, Lean proves \emph{Change Signature Soundness}: every runtime semantic effect is contained in the statically inferred signature. Composing this result with semantic capability admission yields an end-to-end theorem that protected executions cannot emit a semantic effect outside their declared policy. The mechanization deliberately models a smaller core than the production implementation; correspondence between the JavaScript analyzer/compiler and the Lean judgments remains future work. Patch does not claim that state transitions, effect systems, capability systems, interval analysis, provenance, or why-oriented debugging are individually new. The research question is whether making semantic change the mandatory mutation representation permits these facilities to share one language-level semantic substrate while preserving a low-complexity surface language.
\end{abstract}

\section{Introduction}
A large fraction of software tooling exists to answer a simple question: \emph{what changed?} Debuggers reconstruct traces, user interfaces maintain undo stacks, event-sourced systems persist events, collaborative applications compare updates, and security tools approximate side effects. General-purpose languages usually begin from a lower-level abstraction: mutate a location, then recover the semantic meaning of that mutation later.

Patch inverts that order. Instead of assignment being primary and change metadata secondary, a semantic change is constructed before a persistent update is committed:

\begin{lstlisting}
create number score = 0

change score:
  add 1
\end{lstlisting}

The source vocabulary remains small, but the runtime can normalize the block to a semantic operation such as \textsc{AddNumber}(score,1). The normalized change can then drive execution, history, generated inversion, preview, replay foundations, conflict reasoning, and GUI state refresh.

Beta 4 exploits the same representation for static contracts and runtime explanations. Consider:

\begin{lstlisting}
allow reward:
  player.score may increase up to 10

make reward(player, bonus number 0..10):
  change player:
    add bonus to score
\end{lstlisting}

The policy is more specific than generic write authority. It permits a bounded semantic increase, not arbitrary replacement or decrease. Because \texttt{bonus} has the declared range $[0,10]$, the analyzer can prove the dynamic increase stays within the policy. A call with an out-of-range value is guarded at runtime in the current implementation.

The same committed delta records causal context. If \texttt{reward} is invoked from a GUI event, history can retain a chain such as
\begin{verbatim}
event bonus clicked -> recipe reward -> change player.score
\end{verbatim}
and \texttt{why score > 100} can replay the recorded Patch history to identify the first transition that made the predicate true.

This paper asks four questions:
\begin{enumerate}[leftmargin=*]
\item Can ordinary persistent mutation be factored through a semantic Change IR without making the source language cumbersome?
\item Can a static semantic Change Signature be proved to over-approximate runtime semantic mutation in a useful structured core?
\item Can operation- and magnitude-sensitive Change Capabilities constrain runtime mutation through that inferred signature?
\item Can the same mandatory change representation support explanation, history, inversion, preview, and GUI state evolution without separate application-specific mutation models?
\end{enumerate}

The contribution is not the individual existence of these mechanisms. Rather, Patch investigates their integration around one mandatory mutation representation, together with progressive disclosure that keeps the semantic machinery optional for beginners.

\section{Language Design}
\subsection{Progressive disclosure}
A beginner can ignore Change IR, policies, range analysis, and provenance:

\begin{lstlisting}
create number lives = 3
change lives:
  remove 1
show lives
\end{lstlisting}

Advanced features inspect or restrict the same program model rather than introducing a second state-management architecture.

\subsection{No persistent-assignment escape hatch}
\texttt{create} introduces a fresh binding. Existing persistent bindings cannot be reassigned through ordinary \texttt{x = e}. Post-creation mutation must occur inside \texttt{change}. The restriction is necessary for a complete semantic history by construction.

\subsection{Semantic mutation vocabulary}
The surface language exposes \texttt{set}, \texttt{add}, \texttt{remove}, and \texttt{clear}. Runtime lowering distinguishes more precise operations when possible. Numeric \texttt{add 5} becomes a positive additive operation; list \texttt{add item} becomes an append operation. This distinction matters because Change Capabilities can grant one semantic operation while denying another write to the same path.

\subsection{One model for console and GUI code}
GUI handlers execute ordinary Patch statements:

\begin{lstlisting}
create number count = 0

window "Counter":
  text "Count: {count}"
  button "Add" as add_button

when add_button clicked:
  change count:
    add 1
\end{lstlisting}

Patch UI therefore does not require a second hidden mutation language.

\section{State-Change Factorization}\label{sec:factorization}
Let persistent state be a map $\sigma : Name \rightarrow Value$, let $\nu(x)$ be the current version of target $x$, and let history be $H=[\delta_1,\ldots,\delta_n]$.

A normalized semantic change is
\[
\delta = \langle x,b,n,v,\Delta,v'\rangle,
\]
where $x$ is the target, $b/n$ are base/new versions, $v/v'$ are before/after values, and $\Delta$ is an ordered sequence of semantic operations. A well-formed delta satisfies
\[
applyOps(\Delta,v)=v' \qquad \text{and} \qquad n=b+1.
\]

Define one persistent commit path:
\[
commit(\delta,\sigma,\nu,H)=
\langle\sigma[x\mapsto v'],\nu[x\mapsto n],H\cdot\delta\rangle.
\]

\paragraph{State-Change Factorization.}
If one operational step in the formal core changes an already-existing persistent binding, the step is witnessed by a well-formed semantic change and produces the target update through the single commit operation.

\paragraph{Mutation Transparency.}
Every such committed mutation appends an inspectable semantic change describing its transition.

The production interpreter has a richer state space and more operations than the current formal core. Thus the mechanized theorem is evidence about the defined core semantics, not yet a verified implementation theorem for all JavaScript runtime paths.

\section{Semantic Change Contracts}
\subsection{Change Signatures}
For a recipe $f$, let
\[
Sig(f)=\{e_1,\ldots,e_k\},
\]
where an effect contains a target/path, semantic operation kind, and optional amount or amount interval. Current operation classes include
\[
\{increase,decrease,add,remove,set,clear\}.
\]

For:
\begin{lstlisting}
make reward(player):
  change player:
    add 5 to score
\end{lstlisting}
Patch infers conceptually:
\begin{verbatim}
reward(player)
  player.score -> increase by 5
\end{verbatim}

Simple production calls are analyzed transitively by substituting callee parameters into caller effects. Unknown callees, recursion, and dynamic targets are conservatively marked unproven in protected contexts.

\paragraph{Change Signature Soundness.}
For the mechanized structured core, define a static inference function $Sig(s)$ and a runtime effect trace $RuntimeChanges(s)$. Lean proves
\[
RuntimeChanges(s) \subseteq Sig(s).
\]
The formal core contains sequencing, nondeterministic branch selection, and bounded repetition. Static inference includes effects from both branch alternatives, so the signature may over-approximate execution, but every actually emitted runtime effect is covered. This closes the signature-coverage assumption for the formal core; it does not yet prove that the production JavaScript analyzer computes exactly the same $Sig$.

\subsection{Change Capabilities}
Let $Cap(f)$ be a set of semantic rules. A policy can state:

\begin{lstlisting}
allow reward:
  player.score may increase up to 10
\end{lstlisting}

A \texttt{set score = 999} is rejected because \texttt{set} is not an \texttt{increase}; an increase whose proven maximum exceeds 10 is also rejected.

The desired static relation is
\[
Sig(f) \subseteq Cap(f).
\]
For the formal structured core, Change Signature Soundness composes with policy admission:
\[
RuntimeChanges(s) \subseteq Sig(s) \subseteq Cap(s),
\]
and therefore
\[
RuntimeChanges(s) \subseteq Cap(s).
\]

Lean proves this end-to-end containment result for the formal core as \texttt{endToEndCapabilitySoundness}. The remaining compiler-level obligation is correspondence between production analyzer output and the formal signature/policy judgments.

\section{Bounded Range Analysis}
Beta 2 rejected bounded dynamic amounts because their magnitude could not be proved. Beta 3 introduced optional numeric parameter intervals, retained in beta 4:

\begin{lstlisting}
make reward(player, bonus number 0..10):
  change player:
    add bonus to score
\end{lstlisting}

The analyzer associates $bonus$ with $[0,10]$ and propagates intervals through simple arithmetic. For example,

\begin{lstlisting}
make reward(player, bonus number 0..5):
  change player:
    add bonus * 2 to score
\end{lstlisting}

produces the interval $[0,10]$. With input range $[0,6]$, the possible result becomes $[0,12]$ and a capability capped at 10 is rejected.

The implemented interval evaluator supports literals, ranged names, unary sign, parentheses, addition, subtraction, multiplication, and division when the divisor interval excludes zero. It is intentionally conservative. This is a lightweight application of established abstract-interpretation/range-analysis ideas, not a novelty claim by itself.

Declared parameter bounds are also enforced at runtime. This is necessary because production signature reasoning relies on the stated range. A later typed compiler should make more call-site obligations statically dischargeable.

\section{Causal Provenance and Why Queries}
Each committed change records source line and active cause context. Recipe calls add recipe frames; GUI dispatch adds event frames. Therefore a change may retain provenance such as
\begin{verbatim}
event bonus clicked -> recipe reward
\end{verbatim}
in addition to the semantic operation itself.

Two initial queries are implemented:

\begin{lstlisting}
why score
why score > 100
\end{lstlisting}

For a target value, Patch reports recorded transitions and known source/recipe/event causes. For a predicate, Patch reconstructs the state before recorded changes and replays semantic history until it finds the first transition from false to true. If the predicate is false now or was already true before recorded changes, it reports that fact.

Why-oriented debugging and provenance are established research areas, including systems such as Whyline \cite{ko2008whyline}. Patch does not claim to invent causal debugging. The research opportunity is that mandatory semantic changes provide a natural provenance carrier without requiring application code to separately instrument ordinary mutation. The current \texttt{why} implementation is historical provenance, not a general counterfactual or causal-inference engine.

\section{Lean 4 Mechanization}
The repository contains a Lean 4 project pinned to Lean 4.30.0. \texttt{PatchFormal.lean} defines values, semantic operations, \texttt{applyOps}, well-formed changes, machine state, a single change step, effect intervals, capability rules, and signature/policy coverage relations. \texttt{PatchSignature.lean} adds a structured control-flow language, static signature inference, and a runtime semantic-effect trace relation.

The current mechanized results are:
\begin{enumerate}[leftmargin=*]
\item \textbf{State-Change Factorization}: every step of the formal machine has a well-formed change witness and updates through the defined commit operation.
\item \textbf{Mutation Transparency}: the witnessing change appears in resulting history.
\item \textbf{Interval containment transitivity}: if interval $A$ is inside $B$ and $B$ is inside $C$, then $A$ is inside $C$.
\item \textbf{Semantic Change Contract composition}: signature coverage plus policy admission implies runtime policy admission.
\item \textbf{Change Signature Soundness}: for the structured control-flow core, every runtime effect belongs to the statically inferred signature.
\item \textbf{End-to-end Capability Soundness}: a protected formal execution cannot emit an effect outside the capability policy admitted by its inferred signature.
\end{enumerate}

CI builds both Lean libraries and rejects source containing unfinished \texttt{sorry} or \texttt{admit} placeholders.

The next formal step is not another set-inclusion lemma. It is an \emph{implementation correspondence} result. We need a relation between production Change IR/analyzer effects and formal \texttt{Effect} values, followed by evidence that the JavaScript analyzer and lowering preserve the proved signature judgments for a useful Patch subset. A verified checker boundary is an alternative if direct compiler verification becomes too costly.

\section{Compiler and Artifact}
The beta 4 pipeline is
\begin{verbatim}
Patch source
  -> parser / AST + range annotations
  -> semantic Change Signature analysis
  -> Change Capability validation
  -> Change IR
  -> .patchapp                [implemented]
  -> bootstrap .wasm          [implemented]
  -> direct Wasm lowering     [next]
  -> native host packaging    [planned]
\end{verbatim}

\subsection{Portable artifacts}
The \texttt{.patchapp} representation contains source, project metadata, Change IR, semantic analysis, and assets. The bootstrap WebAssembly backend emits a valid instantiable module containing compiled Patch payload for a Patch host. It is not yet direct lowering of every Change IR instruction to executable Wasm.

\subsection{Patch Studio}
Patch Studio is a browser-first PWA for desktop browsers and iPhone/iPad. It provides editor, console/window execution, GUI preview, first visual Designer controls, Change IR inspection, and a Change Contract view. It displays ranged parameters and proven amount intervals. Since \texttt{why} is normal Patch syntax, causal explanations are also available when running code in Studio.

\section{Related Work and Novelty Boundary}
Patch occupies a crowded design space. Broad firstness claims would be incorrect.

\subsection{First-class state and state transitions}
Plaid makes abstract object state changes a first-class language concept \cite{sunshine2011plaid}. Worlds reifies program state and supports scoped speculative side effects and commit/discard behavior \cite{warth2011worlds}. Patch therefore does not claim to invent state transitions, reified state, speculation, or undo. Its candidate distinction is the mandatory structured delta through which ordinary persistent mutation executes and from which multiple analyses are derived.

\subsection{Effect and capability systems}
Classical type-and-effect systems infer conservative side-effect approximations \cite{lucassen1988effects}. Effekt relates effects and capabilities \cite{brachthaeuser2020effects}. Patch does not claim that effects or capabilities are new. Its research question concerns operation-sensitive semantic transitions derived from the same Change IR that is used for mutation itself, including distinctions such as \emph{increase by at most 10} versus \emph{set arbitrary value} on the same storage path.

\subsection{Edit calculi, patch theory, and distributed updates}
Edit Lenses make edits explicit and translate them between related structures \cite{hofmann2012edit}; higher-order change structures support incremental computation \cite{cai2014changes}; formal patch theories study composition and commutation \cite{angiuli2016patch}. CRDTs provide convergence for specific replicated data types \cite{shapiro2011crdt}. Patch borrows the broad insight that changes deserve semantic structure but currently makes no general convergence claim.

\subsection{Provenance and why-oriented debugging}
Whyline demonstrates the utility of asking why and why-not questions about program behavior \cite{ko2008whyline}. Patch's initial \texttt{why} facility is narrower. It explains facts from recorded semantic state transitions and associated recipe/event provenance. The question for evaluation is whether a mandatory change representation makes useful explanations easier to obtain and more complete for persistent state mutation.

\subsection{Educational languages}
Scratch demonstrates the value of designing representations around accessibility and immediate feedback \cite{resnick2009scratch}. Patch's educational hypothesis is that stronger semantic structure need not impose a more difficult beginner surface.

\section{Evaluation Plan}
A high-venue submission should combine formal, systems, security, and usability evidence.

\paragraph{RQ1: Factorization coverage.}
Generate a conformance corpus for every persistent mutation under sequence, conditionals, loops, recipes, preview, and GUI events. Verify that supported post-creation state differences correspond to semantic changes.

\paragraph{RQ2: Signature soundness and compiler correspondence.}
The formal core theorem is now mechanized. The next evaluation should compare production analyzer signatures against manually labeled and dynamically observed effects, and build a machine-readable correspondence corpus between JavaScript Change IR effects and Lean effects. Missed runtime changes are correctness failures; conservative over-approximation is measured separately.

\paragraph{RQ3: Capability enforcement and ranges.}
Construct positive/negative security cases for counters, balances, inventories, plugin-like modules, nested calls, and arithmetic range expressions. Measure proved, rejected, and unproven cases. At least one case study should demonstrate a bug or policy violation prevented by operation- or magnitude-sensitive authority that would require explicit application checks in a conventional implementation.

\paragraph{RQ4: Explanation usefulness.}
Build seeded state bugs and compare Patch provenance with ordinary logging approaches. Measure whether \texttt{why} identifies the responsible transition, how much extra instrumentation baselines require, and where history-only explanation is insufficient.

\paragraph{RQ5: Performance.}
Separate interpreter overhead, compile-time analysis cost, change-recording cost, and later direct-Wasm performance.

\paragraph{RQ6: Novice comprehension.}
If accessibility remains a central empirical claim, use a preregistered randomized/counterbalanced study comparing Patch and conventional mutable snippets. Tasks should include predicting outputs, identifying mutations, interpreting a denied capability, and tracing a state bug. Measure correctness, completion time, edits, confidence, and cognitive load.

\section{Limitations and Threats}
The current type system is lightweight. Interval analysis is intentionally small and path-insensitive. It cannot prove many nonlinear, data-dependent, or recursive cases. Runtime parameter guards are part of the present production contract story. Transitive production signature analysis handles only a restricted call model. Whole before/after snapshots are inefficient for large structures. \texttt{why} reasons from recorded history and does not establish counterfactual causation. External I/O is outside current replay and capability theorems. Direct Change-IR-to-Wasm execution and native packages are not yet implemented.

The Lean model is a formal core, not a verified extraction of the JavaScript compiler. State-Change Factorization, Change Signature Soundness, and end-to-end capability containment are mechanized for the formal semantics, but no theorem yet states that every production compiler result corresponds to those formal judgments. Claims about production soundness must therefore remain conditional until a correspondence proof, translation validation approach, or verified checker bridges the implementation and formalization.

Finally, novelty remains conditional on systematic related-work review. Behavioral and graded effect systems, object capabilities, refinement/range types, provenance systems, reversible update languages, and domain-specific update calculi may contain closer precedents. The submission must test the proposed combination rather than rely on terminology.

\section{Conclusion}
Patch asks what changes if semantic mutation becomes a language-level object before state is updated, rather than metadata reconstructed afterward. State-Change Factorization makes a semantic delta the required route for persistent mutation. Semantic Change Contracts reuse that representation to infer operation-sensitive effects and constrain them with optional policies. Bounded range analysis adds magnitude reasoning; provenance and \texttt{why} expose the history carried by the same change representation.

Beta 4 strengthens the formal story substantially. For a structured Lean core, the project now proves that runtime semantic effects are covered by static Change Signatures and that protected executions cannot escape an admitted semantic capability policy. The remaining bridge is between that formal core and the production analyzer/compiler. The broader hypothesis is that one mandatory semantic change representation can simultaneously support safer mutation, richer tooling, and a simple beginner-facing language. High-venue claims will depend on production correspondence, direct compiled execution, systematic evaluation, and careful comparison with the closest prior systems.
