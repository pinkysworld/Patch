\title{Patch: State-Change Factorization for Transparent Mutable Programs}
\author{Mich\'el Nguyen}
\date{Beta artifact manuscript, August 2026}

\begin{document}
\maketitle

\begin{abstract}
Programming languages typically expose mutation through assignment or data-structure-specific operations and reconstruct the meaning of state transitions later for debugging, undo, replay, synchronization, or auditing. Patch explores a different factorization: post-creation persistent mutation is compiled into and executed through a normalized semantic change representation. The source language remains deliberately small---a programmer writes \texttt{change score: add 1}---while the compiler/runtime constructs a structured delta describing the target, version transition, semantic operations, before/after values, and generated inverse operations where supported. We call the central prospective property \emph{State-Change Factorization}: every supported persistent state transition from $S$ to $S'$ must occur through a semantic change $\delta$ such that $apply(\delta,S)=S'$, with no ordinary persistent-assignment escape hatch. The same Change IR drives execution, history, preview, undo/redo, replay foundations, GUI state evolution, and conservative conflict reasoning. This claim is intentionally narrower than ``first-class state change'': Plaid, Worlds, change-oriented programming environments, edit transactions, lenses, incremental change structures, reversible systems, and patch theories provide substantial prior art. We describe the Patch 0.2 artifact, including its interpreter, compiler front end, portable \texttt{.patchapp} format, bootstrap WebAssembly target, browser-first Patch Studio, and first GUI/visual-designer slice. We give a core semantic model and state proof targets for factorization, inversion, preview non-interference, replay, and commutation. The manuscript reports implemented mechanisms and a falsifiable evaluation plan; mechanized proofs, direct Change-IR-to-Wasm execution, performance results, and novice-study results remain future work rather than fabricated findings.
\end{abstract}

\section{Introduction}
A large fraction of software tooling exists to answer a deceptively simple question: \emph{what changed?} Debuggers reconstruct traces, user interfaces maintain undo stacks, event-sourced applications persist events, collaborative tools compare edits, and observability systems attempt to infer which operation produced a state transition. Yet general-purpose languages usually begin from a lower-level abstraction: mutate a location, then infer the semantic meaning of that mutation later.

Patch asks whether the relationship can be inverted. Instead of assignment being primary and change metadata secondary, Patch makes semantic change the route through which persistent application state evolves:

\begin{lstlisting}
create number score = 0

change score:
  add 1

show score
\end{lstlisting}

The programmer sees a small vocabulary. Internally, the \texttt{change} block is normalized before commit into a delta such as an \textsc{AddNumber} operation over a versioned target. The implementation can derive an inverse, retain history, preview the transition without committing it, replay a deterministic change sequence, and compare selected pairs of changes for commutation.

The project is motivated by two simultaneous goals that are usually treated separately. First, Patch investigates whether a structured change representation can be made a semantic invariant of ordinary mutable programming. Second, Patch attempts to keep the surface language simple enough that a beginner does not need to understand edit algebras, command objects, event sourcing, ownership, or compiler IRs.

The central research question is therefore:

\begin{quote}
Can ordinary persistent mutation in a low-complexity general-purpose language be factored through a semantic Change IR, so that useful correctness and tooling properties follow from the language semantics rather than from application-specific logging infrastructure?
\end{quote}

The current artifact makes five concrete contributions. First, it provides a language design in which existing persistent bindings cannot be directly reassigned outside \texttt{change}. Second, it lowers change blocks to a normalized Change IR and executes runtime state transitions through corresponding semantic operations. Third, the same representation supports history, generated inverses, preview, undo/redo, replay foundations, GUI state refresh, and conservative conflict reasoning. Fourth, Patch Studio provides a browser-first integrated environment, including an installable mobile PWA, console/window execution, a first source-preserving visual Designer, and portable application builds. Fifth, this paper states a formalization and empirical program intended to determine whether the design is actually novel, correct, usable, and performant.

\section{Design Principles}
\subsection{Progressive disclosure}
A beginner should be able to write ordinary programs without learning the internal change calculus. The source vocabulary emphasizes ordinary words such as \texttt{create}, \texttt{change}, \texttt{add}, \texttt{remove}, \texttt{show}, \texttt{window}, and \texttt{when}. Version numbers, inverse operation sequences, conflict metadata, and compiler IR remain inspectable advanced concepts rather than prerequisites.

\subsection{Creation is distinct from mutation}
\texttt{create} introduces a fresh persistent binding. The main factorization theorem concerns post-creation mutation of an existing binding. This distinction keeps the theorem precise: extending the store domain is not conflated with changing a value already present in the store.

\subsection{No persistent-assignment escape hatch}
If a language allowed both \texttt{change x} and ordinary reassignment \texttt{x = e}, its semantic change history could be incomplete by construction. Patch therefore rejects direct reassignment of existing persistent bindings. Assignment-like syntax is limited to declaration contexts such as fields inside \texttt{create thing}.

\subsection{The semantic change is the mutation mechanism}
Patch is not intended to perform an ordinary write and then emit a log record. A change is normalized first; commit applies that change to persistent state. This order is essential to the State-Change Factorization claim.

\subsection{One language for console and GUI state}
GUI programs use the same variables and \texttt{change} semantics as console programs:

\begin{lstlisting}
create number count = 0

window "Counter":
  text "Count: {count}"
  button "Add" as add_button

when add_button clicked:
  change count:
    add 1
\end{lstlisting}

The event handler does not mutate hidden GUI state through a second language. It executes ordinary Patch statements, after which the UI is re-rendered from application state.

\section{Language Overview}
Patch 0.2 provides numbers, text, booleans, lists, record-like ``things,'' conditions, repetition, small recipes/functions, semantic-change inspection, and an initial event-driven GUI model.

\begin{lstlisting}
create text hero = "Mia"
create list inventory = key, map

create thing player:
  name = "Mia"
  score = 0
  lives = 3

change player:
  add 10 to score
  remove 1 from lives
\end{lstlisting}

Control flow is conventional:

\begin{lstlisting}
if player.lives > 0:
  show "keep playing"
else:
  show "game over"

repeat 3:
  change player:
    add 1 to score
\end{lstlisting}

\subsection{History, watch, and inverse operations}
\begin{lstlisting}
watch score

change score called bonus:
  add 10

history score
undo bonus
redo
\end{lstlisting}

The beta restricts named undo to the latest change because arbitrary selective undo requires a sound rebasing or commutation model. This limitation is explicit rather than hidden behind unsafe behavior.

\subsection{Preview}
\begin{lstlisting}
preview:
  change score:
    add 100
\end{lstlisting}

Preview evaluates against cloned state/history, reports the proposed transition, and restores committed state. The formal target is not merely ``preview seems to work,'' but a non-interference and agreement property stated in Section~\ref{sec:formal}.

\section{State-Change Factorization}\label{sec:formal}
We define a deliberately small semantic core before extending it to the full beta language. Let persistent state be a finite map
\[
\sigma : Name \rightarrow Value,
\]
let $\nu(x)$ be the current version of target $x$, and let history be an ordered sequence $H=[\delta_1,\ldots,\delta_n]$.

A normalized semantic change is
\[
\delta = \langle x,b,n,v,\Delta,v'\rangle,
\]
where $x$ is the target, $b$ and $n$ are base/new versions, $v$ and $v'$ are before/after values, and $\Delta$ is an ordered sequence of semantic operations.

Representative operations include
\[
\Delta ::= Set(v) \mid AddInt(k) \mid RemoveInt(k) \mid AppendText(t) \mid Clear.
\]

Write $applyOps(\Delta,v)=v'$. A well-formed change must satisfy
\[
applyOps(\Delta,v)=v' \qquad\text{and}\qquad n=b+1.
\]

\subsection{Single commit path}
Define the semantic commit function
\[
commit(\delta,\sigma,\nu,H)
=
\langle \sigma[x\mapsto v'],\nu[x\mapsto n],H\cdot\delta\rangle,
\]
subject to $\sigma(x)=v$, $\nu(x)=b$, and $applyOps(\Delta,v)=v'$.

The core language intentionally contains no rule that directly writes a new value to an existing persistent binding. \texttt{create} can extend the store; \texttt{change} is the only post-creation mutation rule.

\subsection{State-Change Factorization theorem target}
For a well-typed source execution
\[
\langle s,\sigma,\nu,H\rangle \rightarrow^{*}
\langle skip,\sigma',\nu',H'\rangle,
\]
if an already-existing persistent target $x$ changes value, then the derivation contains a committed $\delta$ targeting $x$ whose semantic operations produce the corresponding transition, and the store update occurs through the commit rule.

The preferred proof route is a stronger step-local lemma:

\begin{quote}
If one operational step changes the value of an already-existing persistent binding, that step is the change-commit rule and appends exactly one well-formed semantic change describing that transition.
\end{quote}

The global factorization theorem follows by induction over the execution derivation. Mutation Transparency is then a corollary rather than the deepest result.

\subsection{Mutation Transparency}
For each committed post-creation mutation, history contains an inspectable delta whose target and before/after values match the corresponding persistent-store transition. In the current interpreter this follows structurally from the parser/AST and commit path; submission-quality work should mechanize the corresponding core property.

\subsection{Inverse correctness}
For the supported invertible fragment, define a generated inverse $inv(\delta)$ and target
\[
apply(inv(\delta),apply(\delta,v))=v.
\]
Numeric addition uses the negated amount; \textsc{Set} retains the previous value; list append/removal records the index/value necessary to construct \textsc{RemoveAt} or \textsc{InsertAt}. Patch does not claim that arbitrary computation is reversible.

\subsection{Preview non-interference and agreement}
Preview should satisfy two distinct properties. First, committed state and history are unchanged after preview. Second, in the deterministic fragment and under identical initial state/inputs, the proposed change sequence produced by preview should agree with the one produced by commit execution. Time, randomness, nondeterministic I/O, and concurrency must be modeled explicitly before this claim can be generalized.

\subsection{Replay consistency}
For the deterministic core, replaying a version-consistent ordered history from the same initial state should reproduce the same final state. This is a property of Patch state evolution, not a claim that arbitrary external effects such as network requests can be replayed safely.

\subsection{Commutation soundness}
Patch's initial conflict relation is intentionally conservative. Different targets, independent record paths, and additive numeric changes on the same path are candidate commuting cases. Competing writes to the same path conflict. The desired theorem is soundness, not completeness:
\[
commute(\delta_1,\delta_2)
\Rightarrow
apply(\delta_2,apply(\delta_1,S))
\equiv
apply(\delta_1,apply(\delta_2,S)).
\]
Patch may refuse to certify pairs that actually commute, but must not certify a non-commuting pair as safe.

\section{Change IR and Compiler Architecture}
Patch 0.2 includes a compiler front end rather than only an interpreter. Source is parsed to an AST and lowered to normalized Change IR. A source block such as

\begin{lstlisting}
change score:
  add 1
\end{lstlisting}

is preserved as a \texttt{CHANGE} instruction containing a target and normalized operation description rather than being erased into an opaque assignment immediately.

The current compilation pipeline is
\begin{verbatim}
Patch source
  -> AST
  -> Change IR
  -> .patchapp               [implemented]
  -> bootstrap WebAssembly   [implemented]
  -> direct Wasm lowering    [next]
  -> native host packaging   [planned]
\end{verbatim}

\subsection{Portable application bundle}
The \texttt{.patchapp} beta format is deliberately transparent JSON containing project metadata, source, Change IR, capabilities, and assets. A future archive encoding can change without altering the logical model.

\subsection{Bootstrap WebAssembly}
Patch 0.2 emits a valid, instantiable WebAssembly module containing project metadata, source, and Change IR in linear memory. The module exports the memory and metadata locating the payload. CI instantiates generated modules and validates recovered Change IR.

This is intentionally described as a \emph{bootstrap} backend. It establishes a portable binary artifact and host boundary, but does not yet lower every Patch operation directly into executable WebAssembly instructions. Presenting it as a complete direct compiler would overstate the artifact.

\section{Patch Studio and GUI Artifact}
Patch Studio is a browser-first Progressive Web App intended to provide a QuickBASIC/Visual-Basic-like integrated experience without requiring a platform-specific development environment. The same Studio runs in desktop browsers and on iPhone/iPad; current browser builds can edit/run Patch, inspect Change IR, preview GUI applications, and build \texttt{.patchapp} or bootstrap \texttt{.wasm} artifacts locally.

The current GUI language includes \texttt{window}, \texttt{text}, \texttt{button}, \texttt{input}, and \texttt{when ... clicked}. The interpreter exposes a virtual Patch UI model, and Studio renders that model in the browser. Button handlers execute ordinary Patch statements, preserving the same state-change semantics as console code.

Patch Studio also contains a first visual Designer toolbox. Adding Text, Button, or Input modifies readable Patch source rather than generating an opaque secondary form language. Drag positioning, resizing, properties, two-way input binding, and richer controls remain future work.

The long-term portability architecture uses WebAssembly plus a small Patch host/runtime for Windows, macOS, Linux, BSD/Unix, and Web. A portable C99 fallback is planned for unusual Unix console targets. Native packages such as Windows \texttt{.exe} and macOS \texttt{.app} are not yet implemented and are therefore not evaluated in this manuscript.

\section{Implementation and Quality Gates}
The beta implementation is dependency-light ECMAScript. Its expression evaluator avoids host-language \texttt{eval}; an indentation-sensitive parser produces a restricted AST; the interpreter maintains persistent state, target versions, semantic history, redo state, watchers, functions, event handlers, and a virtual UI model.

The repository's CI matrix runs on Windows, macOS, and Linux with Node.js 22 and 24. The current quality gate performs syntax checks, language/compiler/UI/Designer/WebAssembly tests, example smoke tests, a portable \texttt{.patchapp} build, a WebAssembly build, deterministic public-site generation, and deployment-integrity validation. At the time of this manuscript revision, the suite contains 32 automated tests and the complete matrix passes. This establishes artifact consistency across those host environments; it does not imply that native Windows/macOS/Linux executables already exist.

\section{Related Work and Novelty Boundary}
Patch sits in a crowded design space. Broad novelty claims would be incorrect.

\subsection{Plaid and first-class state change}
Plaid explicitly makes changing abstract object states a language concept and provides formal semantics for state transitions and state composition \cite{sunshine2011plaid}. Patch therefore does not claim to invent first-class state change or state-oriented programming. The proposed distinction is that Patch's ordinary persistent value mutation factors through a structured delta/Change IR whose operation content is reused across execution and multiple tooling facilities, rather than primarily representing abstract typestate transitions. This distinction requires detailed semantic comparison before submission.

\subsection{Worlds and first-class program state}
Worlds reifies program state as a first-class object, captures side effects in nested worlds, and supports commit/discard behavior useful for experimentation and undo \cite{warth2011worlds}. Patch cannot claim that reified state, speculative state evolution, or automatic undo are new. Patch instead proposes structured per-mutation deltas as the required update path, rather than whole-world snapshots as the principal abstraction.

\subsection{Change-oriented programming and edit transactions}
COPE and earlier change-oriented programming work treat software-development/source transformations as first-class changes \cite{dig2016cope}. Edit Transactions provide dynamically scoped change sets for controlled live updates to program/system definitions \cite{mattis2017edittransactions}. Patch's research object is ordinary runtime application-state mutation, not primarily source evolution. Nevertheless these systems are close conceptual neighbors and invalidate any claim that Patch invented ``change-oriented programming.''

\subsection{Reducers, event sourcing, and command architectures}
Message/reducer architectures and event sourcing centralize transitions and can naturally enable history or replay. Patch must therefore demonstrate more than syntactic centralization. The proposed PL contribution is the semantic guarantee that existing persistent bindings cannot bypass the Change IR through ordinary reassignment and that the compiler derives the structured delta representation rather than requiring application code to implement its own event/command protocol.

\subsection{Edit lenses and bidirectional programming}
Edit lenses explicitly represent edits and translate edits between related structures \cite{hofmann2012edit}; HOBiT makes lens-style consistency programmable \cite{matsuda2018hobit}. Patch does not begin from a source/view consistency problem, but this work demonstrates that semantic edits are a mature abstraction and must be reflected in Patch's change algebra.

\subsection{Change structures and incremental computation}
Cai et al. develop a theory in which derivatives map input changes to output changes for incremental computation \cite{cai2014changes}; self-adjusting computation similarly tracks dependencies and efficient update propagation \cite{acar2013selfadjusting}. Patch currently targets explicit runtime state evolution and transparency rather than automatic incremental recomputation.

\subsection{Patch theory and CRDTs}
Formal patch theories study composition, inversion, identity, commutation, and conflict \cite{anguilhomotopical2016}. CRDTs provide convergence for specific distributed update types \cite{shapiro2011crdt}. Patch borrows the general insight that changes deserve semantic structure but makes no general CRDT convergence claim. Its current conflict analysis is local and conservative.

\subsection{Educational languages}
Scratch demonstrates the importance of accessible representations and immediate feedback \cite{resnick2009scratch}. Patch's educational hypothesis is narrower and must be tested: making mutation linguistically explicit through \texttt{change} may help novices reason about state while simultaneously enabling semantic tooling. This is an empirical question, not an assumption.

\subsection{Candidate novelty claim}
The defensible candidate claim is therefore the following combination: post-creation persistent mutation is executed through a normalized semantic Change IR with no assignment escape hatch; each change has structured operation content; the same representation drives several runtime/tooling facilities; and the algebra is hidden from the beginner surface. A systematic review must still determine whether an earlier language already satisfies the central parts of this combination. If it does, the claim must be narrowed further.

\section{Evaluation Plan}
The artifact enables a multi-axis evaluation rather than relying on aesthetic arguments.

\subsection{RQ1: Expressiveness and ceremony}
Implement at least 50 console and GUI programs in Patch and conventional baselines such as JavaScript/Python. Measure source size, number of mutation constructs, and helper infrastructure required to provide history, undo, preview, and replay-like behavior.

\subsection{RQ2: Factorization and change-law correctness}
Mechanize the small core, preferably in Lean 4, and prove the step-local factorization lemma, State-Change Factorization, inverse correctness for the declared fragment, preview non-interference, and commutation soundness for the initial certified relation. Property-based tests should complement proofs for the implemented richer language.

\subsection{RQ3: Derived tooling}
Measure how much functionality is obtained from the common Change IR without application-specific history/undo plumbing: inverse coverage, preview correctness, replay reconstruction, change inspection, GUI refresh, and conflict explanation.

\subsection{RQ4: Novice comprehension}
Run a randomized/counterbalanced study comparing equivalent Patch and conventional mutable programs. Tasks should cover output prediction, identification of state-changing operations, modification, debugging, tracing nested updates, and GUI event behavior. Measure correctness, completion time, edit/error count, confidence, and cognitive load. Hypotheses and exclusions should be preregistered.

\subsection{RQ5: Performance}
Benchmark interpreter overhead and, separately, direct compiled WebAssembly once implemented. Workloads should include numeric loops, list changes, record updates, event loops, and configurations with/without history/inverse retention. Interpreter speed must not be presented as the language's compiler ceiling.

\subsection{RQ6: Conflict analysis}
Use a labeled corpus of paired changes including independent targets, independent fields, commuting additions, competing writes, list edits, and nested structures. Measure soundness and conservatism; false ``safe'' classifications are more serious than conservative conflicts.

\section{Limitations}
Patch 0.2 remains a research beta. The type system is mostly dynamic; direct Change-IR-to-Wasm execution is not yet implemented; native desktop packaging is planned rather than complete; snapshot retention is inefficient for large structures; arbitrary selective undo is absent; GUI controls are limited; the visual Designer is an initial toolbox rather than a full RAD form editor; external effects are outside the replay/undo theorem targets; and no controlled novice study has yet validated the accessibility hypothesis.

Most importantly, novelty is not established merely by implementing the artifact. Plaid, Worlds, change-oriented programming, edit transactions, edit lenses, reducer architectures, and patch theories cover neighboring territory. A top-venue claim requires a systematic literature review and external specialist scrutiny in addition to formal and empirical results.

\section{Conclusion}
Patch investigates a specific inversion of the usual relationship between mutation and tooling. Instead of allowing arbitrary persistent writes and reconstructing semantic changes afterward, it attempts to make a structured semantic delta the route through which ordinary persistent state evolves. The current artifact demonstrates that this discipline can coexist with a deliberately small source language, an integrated browser/mobile IDE, an event-driven GUI model, portable application bundles, and an initial WebAssembly target.

The strongest prospective contribution is State-Change Factorization, with Mutation Transparency and change-law properties derived from the same core. The project does not claim to invent state transitions, undo, first-class state, patches, lenses, or change-oriented programming. Whether the narrower factorization discipline is sufficiently novel and useful for a high-end programming-languages contribution now depends on mechanized semantics, direct compiled execution, systematic prior-art analysis, and measured evaluation. Patch 0.2 provides the artifact on which those questions can be answered rather than assumed.
