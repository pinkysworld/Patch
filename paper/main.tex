\title{Patch: State-Change Factorization and Semantic Change Contracts for Transparent Mutable Programs}
\author{Mich\'el Nguyen}
\date{Beta artifact manuscript, August 2026}

\begin{document}
\maketitle

\begin{abstract}
Programming languages usually expose mutation through assignment or data-structure-specific operations and reconstruct the meaning of state transitions later for debugging, undo, replay, synchronization, auditing, or security analysis. Patch explores a different factorization: post-creation persistent mutation is compiled into and executed through a normalized semantic change representation. The source language remains deliberately small---a programmer writes \texttt{change score: add 1}---while the compiler/runtime constructs a structured delta describing the target, version transition, semantic operation, before/after values, and generated inverse where supported. We call the central prospective property \emph{State-Change Factorization}: every supported persistent transition from $S$ to $S'$ occurs through a semantic change $\delta$ such that $apply(\delta,S)=S'$, with no ordinary persistent-assignment escape hatch.

Patch 0.2 beta.2 adds a second layer: \emph{Semantic Change Signatures} are inferred from recipe bodies, and optional \emph{Change Capabilities} constrain the kinds and magnitudes of semantic changes a recipe may produce. For example, \texttt{player.score may increase up to 10} permits a bounded increase while rejecting replacement with \texttt{set score = 999}. Conceptually, the compiler checks $ProducedChanges(f) \subseteq AllowedChanges(f)$. This is deliberately more specific than generic read/write authority or conventional effect tracking. The artifact includes an interpreter, compiler front end, Change IR, portable \texttt{.patchapp}, bootstrap WebAssembly target, browser-first Patch Studio, GUI preview, visual Designer, Change Contract view, and cross-platform CI. We state formal proof targets for factorization, signature soundness, capability soundness, inversion, preview, replay, and commutation. Mechanized proofs, direct Change-IR-to-Wasm execution, performance results, and human-subject results remain future work rather than fabricated findings.
\end{abstract}

\section{Introduction}
A large fraction of software tooling exists to answer a simple question: \emph{what changed?} Debuggers reconstruct traces, user interfaces maintain undo stacks, event-sourced systems persist events, collaborative applications compare edits, and security tools approximate side effects. Yet general-purpose languages usually begin from a lower-level abstraction: mutate a location, then infer the semantic meaning of that mutation later.

Patch asks whether that relationship can be inverted. Instead of assignment being primary and change metadata secondary, Patch makes semantic change the route through which persistent application state evolves:

\begin{lstlisting}
create number score = 0

change score:
  add 1
\end{lstlisting}

The programmer sees a small vocabulary. Internally, the block is normalized before commit into a semantic delta such as \textsc{AddNumber}(score,1). That representation can drive execution, inversion, history, preview, replay foundations, conflict reasoning, and GUI state refresh.

Patch 0.2 beta.2 builds a further idea on top of this invariant. Since the compiler already knows that a recipe performs a semantic operation such as \emph{increase}, \emph{decrease}, \emph{set}, or \emph{clear}, it can infer a semantic Change Signature. The programmer may then optionally state a policy:

\begin{lstlisting}
allow reward:
  player.score may increase up to 10

make reward(player):
  change player:
    add 5 to score
\end{lstlisting}

The policy does not merely grant ``write player.score.'' It grants a narrower semantic authority: increasing that path by at most ten. A replacement, a decrease, or a statically known increase above the bound is rejected.

The main research questions are therefore:

\begin{enumerate}[leftmargin=*]
\item Can ordinary persistent mutation be factored through a semantic Change IR without making the source language cumbersome?
\item Can the compiler soundly infer semantic Change Signatures that over-approximate the changes a recipe may commit?
\item Can optional Change Capabilities constrain semantic mutation more precisely than generic write authority while remaining understandable and useful?
\item Can the same representation support multiple runtime/tooling facilities with less duplicated application infrastructure?
\end{enumerate}

The current artifact contributes an implemented language/compiler path and a falsifiable formal and empirical program. It does not claim that patches, first-class state change, effect systems, capabilities, typestate, undo, or event sourcing are new.

\section{Language Design}
\subsection{Progressive disclosure}
Patch is intended to keep sophisticated machinery beneath a small surface language. A beginner can ignore Change IR and capabilities entirely:

\begin{lstlisting}
create number lives = 3
change lives:
  remove 1
show lives
\end{lstlisting}

Advanced users can inspect or constrain the inferred semantics without changing the basic programming model.

\subsection{No persistent-assignment escape hatch}
\texttt{create} introduces a new binding. Existing persistent bindings cannot be reassigned with ordinary \texttt{x = e}. Post-creation mutation must appear inside \texttt{change}. This is required for the semantic history to be complete by construction.

\subsection{Semantic mutation vocabulary}
The beta surface provides \texttt{set}, \texttt{add}, \texttt{remove}, and \texttt{clear}. Runtime lowering distinguishes more precise operations when types/values make them evident. Numeric \texttt{add 5}, for example, becomes a positive additive operation; list \texttt{add item} becomes an append operation.

\subsection{Recipes and GUI events}
Patch recipes use \texttt{make}/\texttt{do}; GUI events execute the same statements as console code:

\begin{lstlisting}
create number count = 0

window "Counter":
  text "Count: {count}"
  button "Add" as add_button

when add_button clicked:
  change count:
    add 1
\end{lstlisting}

There is no separate hidden GUI mutation language.

\section{State-Change Factorization}\label{sec:factorization}
Let persistent state be a finite map
\[
\sigma : Name \rightarrow Value,
\]
let $\nu(x)$ be the version of target $x$, and let history be $H=[\delta_1,\ldots,\delta_n]$.

A normalized semantic change is
\[
\delta = \langle x,b,n,v,\Delta,v'\rangle,
\]
where $x$ is the target, $b/n$ are base/new versions, $v/v'$ are before/after values, and $\Delta$ is an ordered sequence of semantic operations. A well-formed delta satisfies
\[
applyOps(\Delta,v)=v' \qquad \text{and} \qquad n=b+1.
\]

Define one persistent commit path:
\[
commit(\delta,\sigma,\nu,H)=
\langle\sigma[x\mapsto v'],\nu[x\mapsto n],H\cdot\delta\rangle.
\]

The intended core theorem is:

\paragraph{State-Change Factorization.}
If a well-typed operational step changes the value of an already-existing persistent binding, that step is the change-commit rule and appends exactly one well-formed semantic delta describing the transition.

The global execution property follows by induction over the derivation. Mutation Transparency then becomes a corollary: every committed post-creation mutation has an inspectable change record whose before/after values correspond to the store transition.

\section{Semantic Change Signatures}
A Change Signature summarizes semantic persistent effects of a recipe. Let
\[
Sig(f)=\{e_1,\ldots,e_k\},
\]
where an effect initially contains
\[
e=\langle target,path,kind,amount?\rangle.
\]
The beta semantic kinds are
\[
kind \in \{increase,decrease,add,remove,set,clear\}.
\]
A statically known numeric magnitude is recorded when available.

For:

\begin{lstlisting}
make reward(player):
  change player:
    add 5 to score
\end{lstlisting}

Patch infers conceptually:

\begin{verbatim}
reward(player)
  player.score -> increase by 5
\end{verbatim}

For a dynamic expression such as \texttt{add bonus to score}, the current analyzer records a less precise \texttt{add} effect because it cannot yet prove a numeric sign or magnitude.

\subsection{Transitive inference}
Patch follows simple recipe calls and substitutes callee parameters into the caller's signature:

\begin{lstlisting}
make add_points(target):
  change target:
    add 5 to score

make reward(player):
  do add_points(player)
\end{lstlisting}

The inferred effect for \texttt{reward} includes \texttt{player.score -> increase by 5} with provenance through \texttt{add_points}. Dynamic targets, unknown callees, and recursive cycles are treated conservatively as unproven rather than silently safe.

\paragraph{Signature Soundness target.}
Every committed semantic change that can arise during supported execution of recipe $f$ must be represented by an effect admitted by $Sig(f)$. The signature may over-approximate behavior; soundness is more important than minimality.

\section{Change Capabilities}
A Change Capability policy declares semantic authority. Let
\[
Cap(f)=\{r_1,\ldots,r_m\},
\]
where a rule is
\[
r=\langle target,path,kind,max?\rangle.
\]
The compiler accepts a protected recipe when the inferred committed signature is covered by the policy:
\[
Sig(f) \preceq Cap(f).
\]

A surface rule is intentionally readable:

\begin{lstlisting}
allow reward:
  player.score may increase up to 10
\end{lstlisting}

The following implementation is accepted:

\begin{lstlisting}
make reward(player):
  change player:
    add 5 to score
\end{lstlisting}

but this one is rejected:

\begin{lstlisting}
make reward(player):
  change player:
    set score = 999
\end{lstlisting}

because \texttt{set} is not covered by an \texttt{increase} authority. Likewise, \texttt{add 25 to score} violates the numeric bound.

\subsection{Conservative bounded checking}
If a rule has a bound, the current compiler accepts only amounts it can prove within that bound. Thus:

\begin{lstlisting}
allow reward:
  player.score may add up to 10

make reward(player, bonus):
  change player:
    add bonus to score
\end{lstlisting}

is rejected in beta.2 because no range proof establishes $bonus\le 10$. Future typed/range analysis can make more dynamic cases provable.

\subsection{Why this is not just write permission}
A conventional write capability normally answers whether code may mutate a resource/location. Patch's Change Capability can distinguish two writes to the same path:

\begin{center}
\begin{tabular}{lll}
\toprule
Operation & Generic write authority & Patch semantic policy \\
\midrule
increase score by 5 & write & may be allowed \\
set score to 999 & write & may be forbidden \\
decrease score by 5 & write & may be forbidden \\
\bottomrule
\end{tabular}
\end{center}

This does not make capability systems themselves novel. The candidate contribution is deriving and constraining \emph{semantic state transitions} from the same mandatory change representation used for execution.

\paragraph{Capability Soundness target.}
If a capability-protected recipe compiles under $Cap(f)$, every committed persistent change it produces in the supported execution model satisfies $Cap(f)$.

A proof can decompose into (1) Signature Soundness and (2) static coverage $Sig(f)\preceq Cap(f)$.

\section{Compiler and Artifact}
Patch 0.2 beta.2 uses the pipeline:

\begin{verbatim}
Patch source
  -> parser / AST
  -> semantic Change Signature analysis
  -> Change Capability validation
  -> Change IR
  -> .patchapp                [implemented]
  -> bootstrap .wasm          [implemented]
  -> direct Wasm lowering     [next]
  -> native host packaging    [planned]
\end{verbatim}

The IR includes normal instructions plus \texttt{changeSignatures} and \texttt{changeCapabilities}. These are distinct from host/runtime capabilities such as \texttt{ui.window}.

\subsection{Portable bundle and WebAssembly}
The \texttt{.patchapp} beta representation is readable JSON containing source, project metadata, Change IR, semantic analysis, and assets. The bootstrap WebAssembly backend emits a valid instantiable module containing the compiled Patch payload for a Patch host. It is intentionally not presented as direct execution of every Patch operation in Wasm yet.

\subsection{Patch Studio}
Patch Studio is a browser-first PWA that runs on desktop browsers and iPhone/iPad. It provides editor, console/window execution, GUI preview, first visual Designer controls, Change IR inspection, and now a \emph{Change Contract} view that displays inferred changes and allowed policies. This makes the compiler's semantic analysis inspectable without forcing it into ordinary beginner syntax.

\subsection{CLI}
The beta exposes:

\begin{verbatim}
patch run program.patch
patch check program.patch
patch changes program.patch
patch build program.patch --target portable
patch build program.patch --target wasm
\end{verbatim}

\texttt{patch changes} prints inferred recipe effects and declared policies.

\section{Derived Runtime Properties}
The same normalized change model supports several additional targets.

\paragraph{Inverse correctness.}
For the declared invertible fragment,
\[
apply(inv(\delta),apply(\delta,S))=S.
\]

\paragraph{Preview non-interference.}
Executing \texttt{preview} leaves committed state/history unchanged.

\paragraph{Preview/commit agreement.}
For deterministic code under identical inputs, the proposed semantic changes under preview should agree with subsequent committed execution.

\paragraph{Replay consistency.}
A version-consistent deterministic history replayed from the same initial state reproduces the same final Patch state.

\paragraph{Commutation soundness.}
If the analyzer certifies two changes as commuting, either application order yields observationally equivalent Patch state. The analyzer may conservatively reject unknown cases.

\section{Related Work and Novelty Boundary}
Patch occupies a crowded research space, so the contribution must be stated narrowly.

\subsection{First-class state and state transitions}
Plaid makes abstract object state changes a first-class language concept and formalizes state transitions \cite{sunshine2011plaid}. Worlds reifies program state and supports scoped speculative side effects and commit/discard behavior \cite{warth2011worlds}. Patch therefore does not claim to invent first-class state, state transitions, speculation, or undo. Its candidate distinction is the mandatory structured delta through which ordinary persistent mutation executes and from which further analysis is derived.

\subsection{Effect systems}
Classical type-and-effect systems infer conservative approximations of side effects and the regions of store they affect \cite{lucassen1988effects}. Patch's Change Signatures are clearly related. The proposed difference is semantic granularity tied to Patch's mutation calculus: the analyzer can distinguish \emph{increase}, \emph{decrease}, \emph{set}, and bounded magnitudes because these operations already exist as semantic changes. This distinction must be compared rigorously rather than asserted as firstness.

\subsection{Effects as capabilities}
Effekt reframes effect types as capabilities required from a context \cite{brachthaeuser2020effects}. Patch does not claim the combination of effects and capabilities is new. Its Change Capabilities instead constrain the set of semantic state transitions a recipe may commit over specific persistent targets/paths, and the policy is checked against an inferred semantic change signature.

\subsection{Edit lenses, changes, and patch theory}
Edit Lenses make edits explicit and translate them between related structures \cite{hofmann2012edit}. Higher-order change structures support incremental computation \cite{cai2014changes}. Formal patch theories study composition, inversion, identity, and commutation \cite{angiuli2016patch}. Patch borrows the broad insight that changes deserve semantic structure, but targets ordinary runtime state mutation and a low-complexity surface language.

\subsection{CRDTs and distributed updates}
CRDTs provide principled convergence for specific replicated data types \cite{shapiro2011crdt}. Patch beta makes no general convergence claim. Its conflict/commutation relation is intentionally conservative.

\subsection{Educational languages}
Scratch demonstrates that programming representations can be designed around accessibility and immediate feedback \cite{resnick2009scratch}. Patch's empirical question is narrower: whether explicit \texttt{change} syntax and inspectable Change Contracts preserve or improve comprehensibility despite a richer semantic backend.

\section{Evaluation Plan}
A high-venue submission should combine formal, systems, security, and usability evidence rather than rely on syntax examples.

\subsection{RQ1: Factorization coverage}
Generate a conformance corpus exercising every persistent mutation under direct sequence, conditionals, loops, recipes, preview, and GUI events. Verify that all supported post-creation mutations correspond to committed semantic changes.

\subsection{RQ2: Signature precision and soundness}
Build a corpus of recipes with direct and transitive changes. Compare inferred signatures against manually labeled semantic effects. Measure false over-approximation while treating missed runtime changes as correctness failures.

\subsection{RQ3: Capability enforcement}
Construct positive and negative security cases: bounded counters, balances, inventory actions, UI permissions, plugin-like modules, and nested helper calls. Test whether forbidden semantic transitions are rejected while permitted ones compile. Dynamic/unproven cases should be reported separately.

\subsection{RQ4: Infrastructure reduction}
Implement small applications in Patch and JavaScript/Python baselines. Compare code/tooling required for history, undo, preview, replay, semantic auditing, and change-policy enforcement.

\subsection{RQ5: Performance}
Measure interpreter and later direct-Wasm overhead of change construction, history recording, signature metadata, and policy checking. Compile-time analysis cost and runtime change-recording cost should be separated.

\subsection{RQ6: Novice comprehension}
Use a preregistered randomized/counterbalanced study comparing equivalent Patch and conventional mutable snippets. Tasks include predicting outputs, identifying what changed, modifying behavior, locating an unauthorized change, and explaining mutation bugs. Measure correctness, completion time, edit count, confidence, and cognitive load.

\section{Limitations and Threats}
The current analyzer is deliberately small. Numeric bounds require statically provable literal magnitudes; dynamic range analysis is absent. Transitive substitution currently handles simple identifier arguments; recursive/dynamic call graphs are conservatively unproven. The type system is still lightweight. Whole before/after snapshots are inefficient for large values. External I/O is not covered by replay/undo claims. Direct Change-IR-to-Wasm execution and native packages are not yet implemented. No mechanized theorem or human-subject result is reported yet.

Most importantly, the novelty claim remains conditional on a systematic literature review. Effect systems, capability systems, typestate, permission systems, behavioral types, and domain-specific update languages may contain closer precedents than identified here. A top-venue paper must survive that comparison.

\section{Conclusion}
Patch asks whether a program can know the semantic meaning of a state transition \emph{before} applying it, rather than reconstructing that meaning afterward. State-Change Factorization makes a semantic delta the required route for ordinary persistent mutation. Patch 0.2 beta.2 then uses that same representation to infer Change Signatures and optionally check Change Capabilities such as ``this recipe may increase this score by at most ten.'' The result is a research direction that combines a simple user-facing language with a structured semantic backend for execution, history, inversion, preview, replay, conflict reasoning, GUI state evolution, and semantic mutation policy. The current artifact demonstrates the mechanism; formal soundness, scalability, performance, and usability remain explicit questions for the next research stage.
