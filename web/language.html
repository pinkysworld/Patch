Patch programming language · 0.2 beta.35

Small syntax. Visible changes.

Patch is a change-oriented programming language where persistent mutation is expressed through explicit semantic change operations. The compiler derives operation- and magnitude-aware Change Contracts from the same source-level substrate.

create number score = 0

change score:
  add 1

show score

Explicit mutation

Persistent state changes are visible in source instead of being hidden inside arbitrary assignment expressions.

Change Contracts

Recipes expose which paths they may change, in which direction, and where provable, by what bounded amount.

Multiple backends

Patch currently targets its interpreter, direct WebAssembly, portable C99, standalone web apps and explicit native desktop application paths.

Why Patch exists

Patch explores whether mutation can be made easier to inspect, constrain, replay and validate by treating change itself as a first-class semantic object. The project combines a small language, Change IR, source-backed GUI design, capability-style constraints and reproducible assurance tooling.

Current formal boundary

Beta.32 introduced invocation-frame-aware direct-Wasm correspondence for the supported finite-call-tree subset. Beta.35 adds product-level browser ListBox multi-selection and does not widen that formal claim. Patch does not claim a fully verified compiler: unsupported parser semantics, JavaScript-to-Wasm lowering, runtime capture and independent frame reconstruction remain outside the Lean-checked boundary.

ListBox selection follows the state type

A ListBox bound to create text remains the existing single-select control and its changed handler receives text. A ListBox bound to create list is multi-select in Patch Studio App Preview and Standalone Window Web, and its changed handler receives a transient list of selected strings.

create list fruits = ["Banana", "Mango"]

window "Fruit Picker":
  listbox "Apple", "Banana", "Cherry", "Mango" as fruits

when fruits changed:
  change fruits:
    set = value

The toolkit selection itself is not persistent Patch state. The example persists it only because the handler executes an explicit semantic change. Current native GUI paths remain fail-closed for list-backed ListBox because Native GUI IR 0.7 does not yet model persistent list state.

Table / Grid stays change-oriented

Table structure and rows live in Patch source. Selecting a row is transient UI interaction; it does not silently create or assign persistent application state.

window "People" as main size 520, 320:
  table "Name", "Role" as people at 24, 64 size 440, 180:
    row "Ada", "Engineer"
    row "Grace", "Scientist"

when people changed:
  show value

Inside changed, value is the selected row as a list of display strings. Persistence still requires an ordinary explicit change. Studio App preview and Standalone Web implement this contract. Direct native AOT carries it through Native GUI IR 0.8/backend 0.9 on Win32, AppKit and GTK3.

Token-free Ready apps and offline Window linking carry the same Table semantics through sealed payload v9/runtime v1.0 on Windows, macOS and Linux. Payload v9 transports Table columns, rows, responsive layout policy and the transient text-list event type without introducing persistent native list state. Payload v8/runtime v0.9 remains an explicit older compatibility contract.
