# Paper

Working manuscript:

**Patch: State-Change Factorization and Semantic Change Contracts for Transparent Mutable Programs**

## Status

This manuscript is tied to **Patch 0.2.0-beta.8**. It remains a research-artifact manuscript, not yet a submission-ready top-venue paper.

Beta 8 moves the machine-checked boundary one step toward source semantics. In addition to proof-free semantic `EvidenceStmt`, generated certificates now contain a separate formal `SourceStmt` that preserves source-level `add`, `remove`, `set`, and `clear`. `formal/PatchSource.lean` validates raw amount bounds, performs semantic direction normalization itself, checks that the source lowering equals the separately emitted semantic evidence, reconstructs the formal Change Signature through `PatchEvidence`, checks it against the separate production signature claim, and applies the verified semantic policy checker.

Implemented research mechanisms now include:

- normalized Change IR 0.6;
- semantic Change Signatures and operation-/magnitude-aware Change Capabilities;
- ranged numeric parameters and production interval analysis;
- State-Change Factorization and Mutation Transparency proofs;
- structured `CoreStmt`, formal `Executes`, and Change Signature Soundness;
- executable verified semantic policy checker;
- proof-free `EvidenceStmt` validated/decoded by Lean;
- machine-checked evidence/formal-signature correspondence;
- **formal `SourceStmt` preserving `add/remove/set/clear`**;
- **Lean source semantic normalization and source/evidence equality checking**;
- **`checkSourceSignature_sound` source-to-formal-signature theorem**;
- **`checkedSourceExecutionCannotEscape` formal source-runtime capability theorem**;
- generated source/evidence/signature/policy certificates;
- Windows/macOS/Linux CI plus explicit Lean 4.30 source/evidence/certificate CI.

## Formal modules

```text
PatchFormal.lean      factorization, state, intervals, effects, policies
PatchSignature.lean   CoreStmt execution + signature soundness
PatchChecker.lean     executable verified semantic policy checker
PatchEvidence.lean    proof-free semantic evidence + signature correspondence
PatchSource.lean      formal source mutation vocabulary + source/evidence correspondence
```

Formal CI explicitly builds all five modules and then compiles a certificate generated by the production JavaScript compiler.

## Current checked chain

For the formal source subset:

```text
SourceStmt(add/remove/set/clear)
      -> Lean semantic normalization
      -> EvidenceStmt
      -> Lean decoding to CoreStmt
      -> formal inferSignature
      -> compare separate production Change Signature claim
      -> verified semantic policy check
      -> formal SourceExecutes runtime containment
```

The key new beta-8 facts are that semantic direction is not solely trusted from the producer and that the formal source/evidence relationship is executable and machine checked.

For example, a source-level `add -5` remains an `add` with raw interval `[-5,-5]` in `SourceStmt`; Lean must normalize it to semantic `decrease [5,5]`, and the separate EvidenceStmt must agree.

## Remaining trust boundary

Beta 8 is **not full compiler verification**. Still unproved:

```text
Patch source bytes
   -> JavaScript parser / production AST
   -> formal SourceStmt extraction
```

and:

```text
Patch expression
   -> production-inferred amount interval
```

Production runtime correspondence with the formal `SourceExecutes` relation is also open.

Thus a beta-8 certificate establishes the checked source-core-to-semantic chain for the **emitted formal SourceStmt and raw ranges**, not yet an end-to-end theorem from arbitrary Patch source bytes through the JavaScript runtime.

## Prior-art boundary

Patch does not claim novelty for source calculi, compiler verification, translation validation, Proof-Carrying Code, effects, capabilities, quantitative analysis, provenance, undo or evidence checking. Those are established areas.

The candidate contribution remains the mandatory semantic mutation factorization and the use of that same representation for operation-/magnitude-aware state-transition contracts. The increasingly checked source/evidence pipeline is assurance infrastructure for evaluating that semantic claim.

## High-venue gate

Before an OOPSLA/PLDI/ICFP-level attempt, the project should still add:

- systematic related-work review;
- production AST → `SourceStmt` assurance for a useful fragment;
- mechanized production interval-analysis soundness;
- production-runtime/formal-trace correspondence;
- direct compiled execution;
- two or three convincing semantic-security/engineering case studies;
- evidence/certificate/checker and runtime overhead measurements;
- reproducibility bundle;
- user evidence only if beginner simplicity remains a headline empirical claim.

The next most valuable formal task is **interval-analysis soundness**, because magnitude-aware semantic authority is one of the strongest candidate technical distinctions.
