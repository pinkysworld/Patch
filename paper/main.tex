\title{Patch: State-Change Factorization and Semantic Change Contracts for Transparent Mutable Programs}
\author{Mich\'el Nguyen}
\address{University of the People}

\begin{abstract}
Patch explores a simple language-design choice: after application state has been created, updating it requires an explicit semantic \emph{Change} rather than ordinary reassignment. A Change records what state is targeted and which semantic operation is applied. The compiler derives a Change Signature from that mutation route, and an optional Change Capability can restrict target, operation, and---for a supported numeric fragment---magnitude. History, undo/provenance tooling, policy checks, and formal evidence are built along the same semantic lineage.

The key formal result connects that architecture rather than merely proving adjacent facts. For a supported singleton numeric Change, Lean 4 derives a contract-level effect from the well-formed committed Change and proves that its quantitative amount equals the actual before/after state delta. If a bounded capability rule allows that effect, the actual committed magnitude lies within the permitted interval. Bounded rules reject unknown magnitude, and the executable rule/signature checker is proved equivalent to the relational policy judgment for the modeled fragment. Additional mechanized results cover normalized signature/policy composition, integer ranges, finite ranked calls, exact bindings, guarded traces, finite transitive call trees, and selected runtime-evidence refinement. Source-to-effect extraction, runtime capture, validators, lowering, and the WebAssembly engine remain explicit trust boundaries.

A deterministic eight-case mechanism-isolation study removes operation and magnitude information while preserving reachable write targets. Four distinctions then disappear that Patch rejects for magnitude, operation direction, transitive magnitude, or unproved magnitude; both variants reject target escape. Two multi-state checkout/loyalty and usage/quota application cases exercise the same dimensions on the direct WebAssembly path. These cases do not establish ecological prevalence or superiority over richer effect, capability, or refinement systems. They show what information the mandatory semantic mutation route makes directly available to the current implementation and formal fragments.
\end{abstract}

\section{Introduction}
Mutable state is concise to program with, but much of the meaning of an update is normally recovered around a write rather than represented by the write itself. Downstream tools may need to know whether a state transition was an increase, decrease, replacement, or clear operation; how large a numeric change may be; which procedure caused it; whether that authority was intended; and which transition should be explained or undone.

Patch investigates a deliberately restricted alternative. After application state is created, ordinary modeled updates use a structured \texttt{change} form:

\begin{lstlisting}
create number score = 0
change score:
  add 1
\end{lstlisting}

In this paper, \emph{application state} means Patch state retained across statements and events during a program execution. It does not imply database or disk durability across process restarts. Transient host/runtime values and GUI-control state are separate unless program source explicitly commits them into application state.

The same mutation vocabulary can support authority more precise than binary write permission:

\begin{lstlisting}
allow reward:
  score may increase up to 10

make reward(bonus number 0..5):
  change score:
    add bonus * 2
\end{lstlisting}

The rule authorizes a bounded increase; it does not authorize an arbitrary \texttt{set} or a decrease on the same target. We call the inferred semantic effect summary a \emph{Change Signature}, the declared authority policy a \emph{Change Capability}, and their checked combination a \emph{Semantic Change Contract}.

The architectural hypothesis is not that effects, capabilities, quantitative bounds, first-class changes, reversible execution, event sourcing, or refinement specifications are new. Several related systems are more expressive than Patch. The question is whether making semantic Change the sole modeled post-creation application-state mutation route provides a useful common lineage from state transition to contracts, history/provenance, and scoped assurance.

\paragraph{Design invariant rather than research question}
State-Change Factorization is a by-construction property of the current formal core: a state-changing machine step commits a well-formed Change, and Mutation Transparency records that Change in history. This is an architectural restriction, not an empirical research question and not a difficult semantic theorem. The scientific questions concern what follows from imposing it.

\paragraph{Research questions}
The paper evaluates three questions:
\begin{enumerate}[leftmargin=*]
\item \textbf{RQ1---Contract linkage:} for a supported numeric mutation fragment, can a contract-level operation/magnitude effect be derived from a well-formed committed Change and related to the actual before/after state delta?
\item \textbf{RQ2---Assurance and implementation correspondence:} which contract, range, finite-call, and runtime-correspondence properties can be machine-checked, and where does the proof-free implementation boundary remain?
\item \textbf{RQ3---Mechanism isolation:} which authority distinctions disappear when operation and magnitude information are deliberately erased while reachable write targets are retained?
\end{enumerate}
RQ3 is intentionally not an ecological-validity question: the constructed ablation cannot establish how often these distinctions occur in real software or whether mandatory Change is superior to conventional mutation plus separate analysis.

\begin{claimboundary}
The paper does not claim a fully verified compiler, complete sandboxing, complete foreign-code confinement, intrinsic program reversibility, user-productivity benefits, or unique expressibility of bounded state relations. It claims a scoped language architecture, a direct formal link between supported committed Changes and bounded contract effects, additional machine-checked assurance fragments, and deterministic artifact evidence about the semantic information retained by that architecture.
\end{claimboundary}

\paragraph{Contributions}
This paper makes five scoped contributions:
\begin{enumerate}[leftmargin=*]
\item a language and machine design in which modeled post-creation application-state updates factor through structured semantic Changes, with the by-construction State-Change Factorization and Mutation Transparency invariants;
\item a mechanized Change-to-contract bridge: for supported singleton numeric Changes, the derived directional effect matches the actual committed before/after magnitude, and a bounded allowed effect constrains that actual magnitude;
\item a formal assurance stack covering normalized effect-signature/policy checking, fail-closed bounded unknown magnitude, executable/relational checker equivalence, integer ranges, and finite exact/interprocedural call traces, with source-to-effect extraction explicitly outside the signature theorem;
\item an implementation bridge showing that selected semantic authority survives finite call propagation and repeated WebAssembly invocation frames, using independently reconstructed evidence and Lean-checkable witnesses, with an explicit trust boundary;
\item a reproducible artifact evaluation comprising an eight-case mechanism-isolation matrix, two multi-state application cases, and an audit of which compiler/runtime consumers reuse the semantic mutation lineage.
\end{enumerate}

\section{Language Design and Boundaries}
\subsection{Surface mutation discipline}
A surface program can omit signatures, policies, certificates, and backend details:

\begin{lstlisting}
create number lives = 3
change lives:
  remove 1
show lives
\end{lstlisting}

\texttt{create} introduces a new application-state binding. Existing application-state bindings are not subsequently updated with ordinary \texttt{x = e}; source-level state-changing code uses \texttt{change}. The compiler lowers a \texttt{change} node to a \texttt{CHANGE} instruction while semantic analysis derives its effect information.

The source-facing mutation verbs are \texttt{set}, \texttt{add}, \texttt{remove}, and \texttt{clear}. Numeric analysis can classify sign-determinate updates more precisely: \texttt{add 5} is an increase and \texttt{add -5} a decrease.

\subsection{Sign-indeterminate operations}
The production language is wider than the current directional Lean bridge. For example:

\begin{lstlisting}
make adjust(delta number -3..3):
  change score:
    add delta
\end{lstlisting}

Because the interval crosses zero, production analysis may retain an \texttt{add}/\texttt{remove}-style operation instead of proving a directional increase/decrease. The current Lean \texttt{ChangeKind} has \texttt{increase}, \texttt{decrease}, \texttt{set}, and \texttt{clear}; the Change-to-contract theorem in Section~\ref{sec:formal-assurance} therefore does not cover this sign-indeterminate source form. The manuscript does not call such a production policy Lean-certified by that bridge.

\subsection{GUI state versus application state}
Patch Studio and Window applications do not make every toolkit mutation part of the language's modeled state. Event-local values, focus/selection, geometry, and toolkit internals are transient unless Patch source explicitly commits a supported Change. A typical boundary crossing is explicit:

\begin{lstlisting}
create number level = 0

window "Mixer" as mixer:
  slider 0..100 as volume step 5

when volume changed:
  change level:
    set = value
\end{lstlisting}

Here the slider's event-local \texttt{value} is transient; \texttt{level} becomes application state only through the explicit \texttt{change}. This boundary is important because GUI toolkit internals are not covered by State-Change Factorization or the direct WebAssembly formal correspondence.

\subsection{A real cost of the restriction}
Removing ordinary application-state assignment is not free. A conventional transfer can update two locations in a compact statement group; Patch currently represents it as two separate semantic commits:

\begin{lstlisting}
change source_balance:
  remove amount
change destination_balance:
  add amount
\end{lstlisting}

This is more explicit but also more verbose, and the two Changes are not a single atomic multi-target transaction. Similar in-place idioms may require restructuring rather than direct reassignment. The present paper does not demonstrate that this trade-off improves usability or productivity; it studies the semantic and assurance consequences of the restriction.

\section{State-Change Factorization and Semantic Change Contracts}
Let application state be a map $\sigma : Name \rightarrow Value$, versions be $\nu$, and history be $H=[\delta_1,\ldots,\delta_n]$. A normalized semantic change is
\[
\delta = \langle x,b,n,v,\Delta,v'\rangle,
\]
where $x$ is the target, $b$ and $n$ are base and new versions, $v$ and $v'$ are before and after values, and $\Delta$ is an ordered sequence of semantic operations. Well-formedness requires
\[
applyOps(\Delta,v)=v' \quad\text{and}\quad n=b+1.
\]

\begin{definition}[State-Change Factorization]
\label{def:factorization}
For every state-changing step in the current Lean machine, there exists a well-formed $\delta$ such that the resulting machine is exactly the modeled commit of $\delta$.
\end{definition}

\begin{definition}[Mutation Transparency]
\label{def:transparency}
The witnessing Change appears in the resulting history.
\end{definition}

These are by-construction invariants: the modeled \texttt{Step} relation admits state-changing steps through the Change commit constructor. Their role is to state the architectural restriction precisely, not to establish a surprising property of arbitrary imperative programs.

For a recipe $f$, a Change Signature conservatively describes normalized semantic effects:
\[
Sig(f)=\{e_1,\ldots,e_k\}.
\]
An effect records target, optional field, semantic operation kind, and optional amount interval. A Change Capability specifies allowed authority over that vocabulary.

\subsection{Direct Change-to-contract bridge}
\label{sec:formal-assurance}
The artifact connects the mutation machine and contract vocabulary in \path{PatchChangeContract.lean}. For a deliberately small singleton numeric Change fragment, \texttt{effectOf} maps a well-formed semantic Change to a contract-level \texttt{Effect}. \texttt{actualAmountFor} independently reconstructs a directional magnitude from the committed before/after values.

For a single numeric \texttt{addInt} or \texttt{removeInt}, the sign determines \texttt{increase} or \texttt{decrease}; a singleton interval records exact magnitude. A single \texttt{set} maps to a non-quantitative set effect. Multi-operation Changes, fields, text/list operations, \texttt{clear}, and sign-indeterminate source ranges are outside this bridge.

\begin{theorem}[Change amount correspondence]
\label{thm:change-amount}
For a well-formed Change $d$ in the supported singleton numeric fragment, if \texttt{effectOf}$(d)=e$ and $e$ is directional, then the amount recorded by $e$ equals the amount reconstructed from the committed before/after values of $d$.
\end{theorem}

\begin{theorem}[Bounded Semantic Change Contract]
\label{thm:change-contract}
Let $d$ be a well-formed supported Change, let \texttt{effectOf}$(d)=e$, and let a rule $r$ with permitted interval $P$ allow directional effect $e$. Then there exists an actual interval $A$ reconstructed from $d$'s committed before/after values such that $A \subseteq P$.
\end{theorem}

This theorem is the formal connection between the mutation-machine Change and the contract-level Effect/Rule vocabulary. It does not prove the production source analyzer: the premise that a source construct corresponds to the supported Change remains part of the source/evidence boundary described below.

\paragraph{Answer to RQ1}
Yes for the stated fragment. The formalization relates a well-formed committed numeric Change to its directional contract effect and proves that a bounded allowed effect constrains the actual committed before/after magnitude. The result is intentionally narrower than the production language.

\section{Formal Assurance Stack}
\subsection{Normalized signature and policy soundness}
The formal control-flow core contains atomic normalized \texttt{Effect} values. Its \texttt{emit} form therefore does \emph{not} prove that target, field, operation, or interval were correctly derived from Patch source. That extraction is validated separately. Within the normalized core, Lean proves that execution cannot emit an effect absent from the inferred branch-union signature, and successful policy checking admits every effect in a protected execution.

Schematically,
\[
Executes(s,r) \Longrightarrow r \subseteq Sig(s),
\]
and if $Sig(s)$ is admitted by policy $P$,
\[
r \subseteq Sig(s) \subseteq P.
\]

\begin{theorem}[Normalized signature/capability soundness]
\label{thm:signature}
For the modeled \texttt{CoreStmt} fragment, every normalized effect atom in an execution trace belongs to the inferred normalized signature; if the verified policy checker accepts that signature, every executed atom has an allowing policy rule.
\end{theorem}

This is a theorem about normalized effects. It is not a proof of the JavaScript source-to-effect analyzer.

\subsection{Executable policy equivalence and fail-closed unknown magnitude}
The relational \texttt{Allows} judgment and executable checker use the same four-case magnitude discipline:
\begin{center}
\begin{tabular}{@{}lll@{}}
\toprule
Effect magnitude & Rule magnitude & Result \\
\midrule
unknown & unbounded & may allow \\
unknown & bounded & reject \\
known & unbounded & may allow \\
known & bounded & require interval containment \\
\bottomrule
\end{tabular}
\end{center}
Thus a bounded capability cannot be satisfied by an unknown quantitative effect. Lean proves both directions for the modeled checker: \texttt{allowsBool = true} iff the relational \texttt{Allows} judgment holds, and the complete signature checker returns true iff \texttt{PolicyAllows} holds. The runtime refinement theorem preserves the magnitude discipline because \texttt{EffectRefines} requires matching presence/absence of amount intervals.

\subsection{Integer range soundness}
For the explicit integer \texttt{RangeExpr} grammar, Lean proves schematically:
\[
EnvRespects(\Gamma,\rho) \wedge analyzeRange(e,\Gamma)=I \wedge eval(e,\rho)=v
\Longrightarrow v\in I.
\]

\begin{theorem}[Integer range soundness]
\label{thm:range}
If the environment respects $\Gamma$ and range analysis returns interval $I$ for a supported integer \texttt{RangeExpr}, every concrete evaluation of that expression lies in $I$.
\end{theorem}

The mechanized grammar includes integer literals, ranged variables, addition, subtraction, negation, and multiplication by a non-negative integer constant. Decimal/floating-point semantics, division, and general multiplication are outside this theorem.

\subsection{Source, guard, and static call-site validation}
The production source path and independent raw-source paths reconstruct supported source/range and guard artifacts separately. Protected certification requires agreement for supported fragments. Numeric range expressions and guards use independent validator-side parsers rather than reusing the corresponding production expression parser.

Concrete call certification also checks static source identity before trusting the production AST's call-site description. An independent raw-source scanner reconstructs supported \texttt{do recipe(args)} sites, including caller/callee identity, source line, order, and exact argument texts. The ordered list must match the separately collected production-AST view before concrete-call witnesses are accepted.

These checks validate translation and source identity; they are not verified JavaScript parsers. Lean checks consequences of the accepted supported evidence.

\section{Finite Exact Recipe Calls}
A local Change Capability is insufficient if a protected recipe can call a helper whose effects silently widen target, operation, or magnitude authority. The finite-call layer therefore tests whether the same semantic authority survives interprocedural propagation rather than treating call analysis as an independent language feature.

The call-assurance stack models finite recipe environments with parameter intervals, semantic signatures, and well-founded ranks. The executable checker validates direct-effect membership, positional argument-interval fit, lower-rank call resolution, and callee-to-caller signature containment. Exact evidence serializes bindings as name/integer pairs so Lean can re-evaluate supported call arguments rather than trusting precomputed constants.

Structured traces cover sequence and literal/static repetition and select exact guards when guards depend only on supported recipe-parameter expressions. Unsupported state-dependent or out-of-fragment guards are not silently certified.

The transitive layer represents a finite selected call tree with exact nested bindings, direct effects, guard choices, static repeats, and strict rank decrease.

\begin{theorem}[Finite transitive call-tree refinement]
\label{thm:calltree}
For a selected finite exact call tree in the encoded fragment, every selected exact effect trace is represented by the caller's semantic signature when the executable structural, binding, range, guard, rank, and containment checks succeed.
\end{theorem}

A representative source shape is:
\begin{lstlisting}
create number score = 0

make leaf(amount number 1..6):
  change score:
    add amount * 2

make middle(value number 0..5):
  do leaf(value + 1)

make caller(bonus number 0..5):
  do middle(bonus)

do caller(2)
\end{lstlisting}

The generated certificate preserves arithmetic expressions and nested bindings for Lean re-evaluation.

\section{Direct WebAssembly Runtime Correspondence}
The runtime layer addresses the dynamic counterpart of the interprocedural question: repeated invocations of the same lexical call chain must remain distinguishable while retaining the effect/signature relationship used by semantic authority.

\subsection{Independent transition/effect validation}
The direct backend lowers a conservative numeric Console subset to WebAssembly. Runtime capture exposes target/before/after transitions. An independent Change-IR executor reconstructs expected transitions and semantic effect occurrences rather than trusting semantic call/effect annotations emitted by the backend.

The validator checks transition order and values, reconstructs lexical change sites and recipe scope, and compares observed semantic effects with production Change Signatures and, where applicable, Change Capabilities. Tampered transitions, signatures, and policies are regression-tested to fail closed. Validator correctness and capture completeness are not Lean-proved.

\subsection{Invocation-frame bridge}
Repeated identical calls require more than one globally scoped effect list. The runtime-correspondence layer therefore reconstructs concrete invocation frames independently of backend call-entry/exit markers. Each frame records caller/callee identity, dynamic invocation ordinal, parent/depth information, exact arguments/bindings, and transition boundaries.

The mixed-guard regression executes three roots in sequence: \texttt{caller(1)}, \texttt{caller(4)}, and \texttt{caller(1)}. Each passes through a four-frame chain. Independent validation reconstructs twelve frames and six supported transitive correspondences. The repeated first/third roots remain distinct dynamic frames while selecting the same branch; the middle root selects the opposite branch.

\begin{theorem}[Observed runtime-frame correspondence]
\label{thm:runtime}
Given accepted independently reconstructed invocation-frame evidence whose bindings equal the exact formal callee bindings, Lean re-evaluates the frame-selected observed effects against the corresponding exact call-tree statement and derives caller-signature refinement when the encoded checks succeed.
\end{theorem}

This is conditional on accepted evidence. It does not establish that the producer of the evidence is correct or complete.

\subsection{Trust boundary}
The runtime bridge is not an end-to-end compiler-refinement theorem. Proof-free or partially validated boundaries include:
\begin{itemize}[leftmargin=*]
\item runtime transition capture completeness;
\item correctness/completeness of independent JavaScript transition/effect validation and invocation-frame reconstruction;
\item source parsing/extraction outside independently cross-checked subsets;
\item the independent JavaScript validators themselves;
\item JavaScript-to-WebAssembly lowering;
\item the WebAssembly engine;
\item Things, GUI/native Window runtimes, foreign code, and unsupported numeric operations.
\end{itemize}

\section{Semantic-Authority Mechanism Isolation}
\subsection{Design}
The evaluation asks a narrow mechanism question: after retaining reachable changed target paths but deliberately erasing semantic operation, magnitude, and proof obligations, which policy distinctions disappear? Eight extension-style micro-cases are run through the real Patch compiler/Change Capability analysis and an intentionally coarse target-only ablation.

The target-only rule is defined independently of Patch's richer decision. For an \texttt{allow} policy $p$ protecting recipe $f$, let
\[
A(p)=\{\,path(r.target,r.field)\mid r\in p.rules\,\}
\]
be the set of target/field paths named by its rules. Let $R(f)$ be the set of target/field paths appearing in \texttt{change} operations reachable from $f$, recursively following known recipe calls and traversing branch bodies. The ablation accepts exactly when
\[
R(f)\subseteq A(p)
\]
for every protected recipe and at least one policy exists. Operation kind, amount, amount range, and range-provability are ignored. Target/field identity and transitive call reachability are retained. A missing protected recipe, an unresolved call, or a recursive call contributes a sentinel escape path and therefore fails closed unless that impossible sentinel were explicitly authorized. This definition matches the artifact implementation used to produce Table~\ref{tab:security-ablation}.

The ablation is constructed to isolate information carried by Patch's semantic effect vocabulary. Consequently, its outcome cannot establish prevalence in real extension ecosystems or superiority to modern effect, capability, or refinement systems. It is evidence about the mechanism, not an ecological benchmark.

\subsection{Two multi-state application cases}
The checkout/loyalty case composes discount and loyalty helpers over multiple state paths. Its safe direct WebAssembly execution terminates with
\[
balance=80,\qquad points=8,\qquad cashback=0.
\]
Controlled variants escalate reward magnitude, reverse balance direction, or target unauthorized cashback state.

The usage/quota case changes domain and models bounded accounting over \texttt{used}, \texttt{remaining}, \texttt{bonus}, and unauthorized \texttt{admin\_credit}. Its safe direct WebAssembly execution terminates with
\[
used=35,\qquad remaining=85,\qquad bonus=5,\qquad admin\_credit=0.
\]
Controlled variants exercise magnitude escalation, direction reversal, and target escape.

These applications are internally authored engineering cases. They are not third-party extensions and do not estimate real-world mutation-pattern frequency.

\paragraph{Answer to RQ3}
In this deterministic corpus, erasing operation and magnitude makes four semantic-authority distinctions disappear while retaining target reachability, whereas target escape remains visible. This supports the limited claim that the retained semantic dimensions matter to the evaluated policy decisions. It does not show that mandatory Change is uniquely capable of recovering those dimensions or that the restriction is broadly practical in existing codebases.

\section{Limitations and Threats to Validity}
\label{sec:limitations}

\paragraph{Formal scope}
The Change-to-contract theorem covers only a small singleton numeric fragment. Fields, multi-operation Changes, collections/text, \texttt{clear}, and sign-indeterminate source ranges are outside it. The normalized signature theorem starts from Effect atoms; source-to-effect derivation remains validated rather than proved.

\paragraph{Implementation trust}
Independent source/range, guard, call-site, transition/effect, and invocation-frame validation reduces selected trust, but those validators are JavaScript rather than verified parsers. Runtime correspondence proves consequences of accepted evidence, not capture completeness, lowering correctness, or WebAssembly-engine correctness.

\paragraph{GUI and foreign state}
GUI control state and toolkit internals are not automatically Patch application state. The source must explicitly commit supported data through \texttt{change} to cross that boundary. Native Window runtimes, Things, foreign code, and unsupported operations are outside the present formal runtime correspondence.

\paragraph{Evaluation construct validity}
The target-only comparison is an internal ablation constructed by deleting the dimensions under study. Its rule is now specified explicitly in Section~7.1 and mirrors the reproducible artifact implementation. It is useful for mechanism isolation but cannot establish comparative superiority or estimate real-world security benefit.

\paragraph{External validity}
The two application cases are internally authored. A public real-code corpus study---for example, measuring which application-state mutation patterns in existing extension/plugin/automation code fit Patch's directional bounded fragment and which fall into the residual category---would materially strengthen the practical-generalization claim. Such a study has not been performed for this manuscript.

\paragraph{Performance validity}
No controlled fixed-machine timing table is reported. The artifact includes a protocol, but methodology is not substituted for results.

\paragraph{Ergonomics and usability}
The mutation restriction can increase verbosity and does not currently provide atomic multi-target Change. No developer study measures learnability, productivity, error rates, or preference. The paper therefore makes no usability claim.

\paragraph{Comparative validity}
Richer effect, refinement, dependent, typestate, reversible, or event-sourced systems may encode properties equal to or stronger than Patch's current contract language. The present work does not implement a modern competing system and therefore makes no performance, annotation-burden, or expressiveness ranking against one.

\section{Conclusion}
Patch explores an architecture in which modeled post-creation application-state mutation is factored through explicit semantic Changes rather than ordinary reassignment. The restriction is by construction; the paper's contribution lies in what can be connected to and derived from it.

For RQ1, the Lean bridge directly connects a well-formed supported committed Change with a directional contract Effect and proves that an allowed bounded rule constrains the actual before/after magnitude. Bounded unknown magnitude is fail-closed, and the executable checker is equivalent to the relational rule/signature policy semantics for the modeled fragment.

For RQ2, the artifact additionally checks normalized signature/policy, integer ranges, finite exact/interprocedural calls, guarded/transitive traces, and selected direct WebAssembly runtime evidence while keeping source analysis, validators, capture, lowering, and engine correctness outside the theorem. The interprocedural and runtime layers specifically test whether the semantic effect/signature relationship survives helper propagation and repeated dynamic invocation. For RQ3, the explicitly defined target-only ablation isolates four policy distinctions that disappear when operation/magnitude are erased, while both variants retain target-escape detection.

The remaining strongest tests are empirical: a real-code mutation corpus, controlled fixed-machine assurance-cost measurement, and a fair implemented/formal comparison with a representative modern effect/capability approach. Those studies would test whether the architectural restriction is broadly practical and cost-effective; the present paper does not assume their outcomes.
