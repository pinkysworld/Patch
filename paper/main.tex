\author{Mich\'el Nguyen}
\date{Beta 35 product artifact / Beta 32 assurance manuscript, August 2026}

\begin{abstract}
General-purpose languages usually expose persistent mutation through assignment or data-structure-specific updates, while auditing, undo, provenance, replay, and policy enforcement reconstruct additional semantic structure around those writes. Patch explores the opposite factorization: ordinary post-creation persistent mutation is represented and committed through a structured semantic \emph{Change}. A programmer writes \texttt{change score: add 1}; ordinary reassignment is not an alternative modeled persistent-update route. We call this property \emph{State-Change Factorization}.

Patch derives \emph{Semantic Change Signatures} and optional \emph{Change Capabilities} from the same mandatory mutation representation. These contracts distinguish target, semantic operation, and, for a supported numeric fragment, magnitude. A component may therefore be authorized to increase \texttt{score} by at most 10 without receiving set or decrease authority over the same target. A Lean 4 development proves factorization, mutation transparency, signature and policy properties, integer range soundness, finite ranked call composition, exact safe-integer call binding, guarded structured traces, and finite transitive exact call-tree refinement for explicit fragments.

The implementation connects production direct-WebAssembly execution to the formal model through independent validation and generated evidence rather than a claim of full compiler verification. Beta 32 reconstructs concrete invocation frames independently of backend call markers, including repeated identical calls. The evidence now also combines repeated root-call identities with different concrete guard paths between them. Generated certificates check each frame binding against the beta 30 exact call tree and let Lean re-evaluate frame-selected observed semantic effects before deriving caller-signature refinement. Supported source/range and guard fragments are independently reconstructed, and supported static \texttt{do recipe(args)} sites are now independently bound from raw source to production-AST call identity before concrete-call witness generation. Runtime capture, independent-validator/frame-reconstruction correctness, remaining parser/extractor semantics, JavaScript-to-WebAssembly lowering, and the WebAssembly engine remain explicit trust boundaries.

The artifact also includes an eight-case semantic-authority ablation, two larger application cases covering checkout/loyalty and usage/quota management, a process-isolated protocol for future controlled overhead/scaling measurements, and a commit-bound reproducibility bundle. No controlled performance result, external plugin-ecosystem result, complete sandboxing result, or end-to-end compiler-verification result is claimed.
\end{abstract}

\section{Introduction}
Mutable programs often need answers beyond the current value of a variable. Debuggers need provenance, interfaces need undo, replay systems need stable transition records, and security mechanisms need to constrain authority. Conventional languages commonly layer these services around writes whose semantic meaning is only partially represented by the language.

Patch asks what changes if the semantic update is primary. Instead of first mutating state and later attaching metadata, a Patch program describes a change that is itself the modeled route to a new persistent state:

\begin{lstlisting}
create number score = 0

change score:
  add 1
\end{lstlisting}

The same mutation vocabulary supports authority more precise than binary write permission:

\begin{lstlisting}
allow reward:
  score may increase up to 10

make reward(bonus number 0..5):
  change score:
    add bonus * 2
\end{lstlisting}

The policy authorizes a bounded increase. It does not authorize an arbitrary \texttt{set}, even though both operations write the same persistent location.

The research question is not whether first-class state change, effects, quantitative typing, capabilities, abstract interpretation, state-transition specifications, procedure semantics, translation validation, or proof-carrying evidence exist. They do, and several related systems are more expressive than Patch along individual dimensions. The narrower question is whether forcing ordinary modeled persistent mutation through one semantic delta representation yields a useful architecture in which execution, operation/magnitude-aware authority, history, provenance, and assurance reuse the same substrate.

The current artifact supports six connected claims:
\begin{enumerate}[leftmargin=*]
\item ordinary post-creation persistent mutation in the modeled language uses structured semantic \texttt{change} operations rather than a separate assignment escape hatch;
\item operation- and magnitude-sensitive Change Signatures and optional Change Capabilities are derived from those mutations;
\item a Lean core proves factorization, signature/policy properties, source/range properties, and finite exact call-tree refinement for explicit formal fragments;
\item production direct-WebAssembly execution is independently validated against Change IR transitions and semantic effects for a conservative supported subset;
\item beta 32 reconstructs concrete invocation frames without trusted backend call markers, distinguishes repeated identical calls even across differing concrete guard paths, and generates Lean-checkable evidence tying frame bindings and observed effects to the beta 30 call tree; and
\item semantic-authority case studies, a controlled-measurement protocol, and a commit-bound reproducibility bundle evaluate and package the implementation without extending the formal theorem beyond its stated boundary.
\end{enumerate}

\section{Language Design}
\subsection{Progressive disclosure}
A beginner can ignore signatures, policies, certificates, and backend details:

\begin{lstlisting}
create number lives = 3
change lives:
  remove 1
show lives
\end{lstlisting}

Advanced machinery derives information from the same source mutation model rather than requiring a second command/event architecture for ordinary persistent state updates.

\subsection{No persistent-assignment escape hatch}
\texttt{create} introduces a fresh persistent binding. Existing persistent bindings are not subsequently updated with ordinary \texttt{x = e}; state-changing source uses \texttt{change}. This syntactic restriction mirrors the single modeled commit route in the formal machine. Transient GUI event values, toolkit selection, and layout state are deliberately not persistent Patch state unless source executes an explicit semantic \texttt{change}.

\subsection{Source and semantic operations}
The source-facing verbs are \texttt{set}, \texttt{add}, \texttt{remove}, and \texttt{clear}. Static semantic analysis can classify numeric mutations more precisely: \texttt{add 5} is an increase, \texttt{add -5} is a decrease, and \texttt{set 5} remains a set. Policies can distinguish these authorities even when they address the same location.

\section{State-Change Factorization and Change Contracts}
Let persistent state be a map $\sigma : Name \rightarrow Value$, let $\nu(x)$ be the current version of target $x$, and let history be $H=[\delta_1,\ldots,\delta_n]$. A normalized semantic change is
\[
\delta = \langle x,b,n,v,\Delta,v'\rangle,
\]
where $x$ is the target, $b$ and $n$ are base and new versions, $v$ and $v'$ are before and after values, and $\Delta$ is an ordered sequence of semantic operations. Well-formedness requires
\[
applyOps(\Delta,v)=v' \quad\text{and}\quad n=b+1.
\]

\paragraph{State-Change Factorization.}
For every state-changing step in the current Lean machine, there exists a well-formed $\delta$ such that the resulting machine is exactly the modeled commit of $\delta$.

\paragraph{Mutation Transparency.}
The witnessing change appears in resulting history.

For a recipe $f$, a Change Signature conservatively describes semantic effects:
\[
Sig(f)=\{e_1,\ldots,e_k\}.
\]
An effect contains target, optional field, semantic operation kind, and optional amount interval. A Change Capability specifies allowed semantic authority. For example, \texttt{score may increase up to 10} distinguishes bounded increase from set or decrease authority.

The novelty hypothesis is not that an equivalent bound is inexpressible in richer effect or refinement systems. It is that Patch derives this restricted authority vocabulary from the same mandatory semantic delta objects through which modeled persistent mutation is committed.

\section{Formal Assurance Stack}
The artifact contains layered Lean modules for semantic changes, signatures, policy checking, source/range evidence, guard validation, abstract calls, exact call binding, exact structured callee traces, finite transitive call trees, and runtime-call correspondence.

\subsection{Signature and capability soundness}
For the structured semantic core, Lean proves a signature property of the form
\[
Executes(s,r) \Longrightarrow RuntimeChanges(r) \subseteq Sig(s).
\]
If every inferred effect is admitted by policy,
\[
RuntimeChanges(s) \subseteq Sig(s) \subseteq Cap(s).
\]
The executable policy checker is proved sound with respect to the relational policy semantics for the modeled fragment.

\subsection{Integer range soundness}
For the explicit integer \texttt{RangeExpr} grammar, Lean proves schematically:
\[
EnvRespects(\Gamma,\rho) \wedge analyzeRange(e,\Gamma)=I \wedge eval(e,\rho)=v
\Longrightarrow v\in I.
\]
The mechanized fragment includes integer literals, ranged variables, addition, subtraction, negation, and multiplication by a non-negative integer constant. Decimal/floating-point semantics, division, and general multiplication are not silently included in this theorem.

\subsection{Source, guard, and static call-site translation validation}
The production source path and independent raw-source paths reconstruct supported formal source/range and guard artifacts separately. Protected certification requires agreement for those supported fragments. Numeric range expressions and guards use independent validator-side parsers rather than reusing the corresponding production expression parser.

Concrete call certification also checks static source identity before trusting the production AST's call-site description. An independent raw-source scanner reconstructs each supported \texttt{do recipe(args)} site's caller recipe, callee, source line, order, and exact trimmed argument texts. That ordered list must match a separately collected production-AST list before concrete-call witnesses are accepted. Call-site evidence is then propagated through the existing structured, transitive, and beta 32 runtime witness layers.

This is translation/source-identity validation, not a Lean proof of either JavaScript parser or scanner. Lean separately checks supported argument semantics after source identity is accepted.

\section{Finite Exact Recipe Calls}
\subsection{Abstract and exact call composition}
\texttt{PatchCalls.lean} models finite recipe environments with parameter intervals, semantic signatures, and well-founded ranks. The executable checker validates direct-effect membership, positional argument-interval fit, lower-rank call resolution, and callee-to-caller signature containment. For modeled rank-decreasing executions, \texttt{callSignatureSoundness} establishes caller-signature coverage.

Concrete evidence serializes exact bindings as name/integer pairs. \texttt{PatchCallSubstitution.lean} re-evaluates call arguments under an exact caller environment and checks positional binding. \texttt{PatchCallRefinement.lean} connects exact values through abstract argument intervals to declared parameter intervals, while \texttt{PatchCallEffect.lean} re-evaluates direct quantitative effects under the exact environment.

\subsection{Structured and guard-selected callee traces}
The beta 28/29 layers move from one quantitative leaf effect to complete exact effect traces over a conservative body language. Sequence and literal/static repetition are represented structurally, and beta 29 adds exact guard selection when guards depend only on supported recipe-parameter expressions. Unsupported state-dependent or out-of-fragment guards fail closed rather than being approximated as verified.

\subsection{Beta 30 finite transitive exact call trees}
Beta 30 extends exact traces through nested ranked recipe calls. \texttt{PatchCallTree.lean} represents a finite selected call tree with exact nested bindings, direct effects, supported guard choices, static repeats, and strict rank decrease. Each nested edge imports the callee semantic signature into its caller.

The principal checked composition is exposed through
\begin{verbatim}
checkedConcreteTransitiveCallTreeRefinesCallerSignature
\end{verbatim}
which establishes that the selected finite exact trace is represented by the caller semantic signature, subject to the encoded fragment and executable checks.

A representative source shape is:
\begin{lstlisting}
create number score = 0

make leaf(amount number 1..6):
  change score:
    add amount * 2

make middle(value number 0..5):
  do leaf(value + 1)

make caller(bonus number 0..5):
  do middle(bonus)

do caller(2)
\end{lstlisting}

The certificate preserves arithmetic expressions and nested bindings for Lean re-evaluation instead of trusting precomputed JavaScript constants.

\section{Direct-WebAssembly Runtime Correspondence}
\subsection{Independent transition and effect validation}
The production direct backend lowers a conservative numeric Console subset to WebAssembly. Runtime capture exposes target/before/after transitions. An independent Change-IR executor reconstructs expected transitions and semantic effect occurrences rather than trusting semantic call/effect annotations emitted by the backend.

The validator checks complete transition order and values, reconstructs lexical change sites and recipe scope, and checks observed semantic effects against production Change Signatures and, where applicable, Change Capabilities. Tampered transitions, signatures, and policies are regression-tested to fail closed.

\subsection{Beta 31 call-aware bridge}
Beta 31 combines the beta 30 exact finite call-tree witness with real direct-WebAssembly execution. Observed semantic effects are validated independently and compared with the selected formal call-tree trace. This narrows the gap between exact call semantics and compiled execution without turning the JavaScript validator or WebAssembly engine into proved components.

\subsection{Beta 32 invocation frames}
A globally scoped effect list is insufficient when the same recipe is invoked repeatedly with identical arguments. Beta 32 therefore reconstructs concrete invocation frames independently of backend call-entry/exit markers. Each frame records caller/callee identity, dynamic invocation ordinal, parent/depth information, exact arguments/bindings, and transition boundaries. Validated effects carry the active frame stack.

For every selected beta 30 call-tree witness, the generated beta 32 certificate checks that the reconstructed frame binding equals the exact formal callee binding:
\begin{verbatim}
runtimeFrameBindings = beta30ExactBindings
\end{verbatim}
Lean then re-evaluates the frame-selected observed effects against the exact call-tree statement through \texttt{evalCallTreeStmtEqBool} before applying
\begin{verbatim}
checkedObservedTransitiveRuntimeRefinesCallerSignature
\end{verbatim}
to conclude caller-signature refinement for the accepted observed list.

The repeated-call regression source \texttt{examples/formal-transitive-calls-repeated.patch} executes two identical root calls. Independent reconstruction assigns distinct dynamic frames, so their effects can be attributed and checked separately without trusted backend call markers.

A stronger regression, \texttt{examples/formal-transitive-calls-mixed-guards.patch}, executes \texttt{caller(1)}, \texttt{caller(4)}, and \texttt{caller(1)} through a four-frame call chain. The first and third invocations are identical and select the same guard branch, while the middle invocation selects the opposite branch. Independent validation reconstructs twelve invocation frames and six supported transitive correspondences. The three \texttt{caller -> outer} witnesses carry distinct dynamic frame identities and bindings 1, 4, and 1, while their selected effects are respectively \texttt{coins +4}, \texttt{score +5}, and \texttt{coins +4}. Lean re-checks each selected trace against its exact call-tree witness.

Generated evidence includes \texttt{GeneratedTransitiveRuntimeCertificate.lean}, \texttt{GeneratedRepeatedTransitiveRuntimeCertificate.lean}, and \texttt{GeneratedMixedGuardTransitiveRuntimeCertificate.lean}.

\subsection{Exact trust boundary}
Beta 32 checks more than beta 31, but it is not an end-to-end compiler refinement theorem. The following remain outside the current Lean proof:
\begin{itemize}[leftmargin=*]
\item correctness/completeness of runtime transition capture;
\item correctness/completeness of the independent JavaScript transition/effect validator and invocation-frame reconstruction;
\item production parser/extractor correctness outside independently cross-checked supported source/range, guard, and static call-site identity fragments;
\item correctness of the independent JavaScript source/range, guard, and call-site validators themselves;
\item JavaScript-to-WebAssembly lowering correctness;
\item WebAssembly-engine correctness.
\end{itemize}

The certificate establishes consequences of accepted, independently reconstructed evidence for the formal fragment. The raw-source call-site check reduces one dependency on production-AST source identity, but it does not prove the production parser correct or validate arbitrary expression semantics. The runtime evidence likewise does not prove that every possible faulty trace would necessarily be captured or reconstructed correctly.

\section{Semantic-Authority Evaluation}
\subsection{Controlled micro-case ablation}
The artifact contains eight extension-style semantic-authority cases. Each case is evaluated by the real Patch compiler/Change Capability analysis and by an intentionally coarse internal ablation that records only transitively reachable changed target paths. The coarse baseline deliberately ignores semantic operation, magnitude, and proof obligations. It is not intended as a model of any named prior effect or capability system.

The expected mechanized decision matrix is:
\begin{center}
\begin{tabular}{lrr}
\toprule
Decision class & Cases & Interpretation \\
\midrule
Patch accept / coarse accept & 3 & both admit the case \\
Patch reject / coarse accept & 4 & semantic authority rejects beyond target-only write authority \\
Patch reject / coarse reject & 1 & target escape rejected by both \\
\bottomrule
\end{tabular}
\end{center}

The four differential rejections cover magnitude escalation, operation-direction escalation, transitive helper magnitude escalation, and fail-closed unknown magnitude. The shared rejection is an unauthorized target escape. These cases support a narrow ablation statement about the artifact's semantic authority dimensions, not a claim of complete malicious-code containment or superiority over prior systems.

\subsection{Checkout/loyalty extension case}
A larger case study models a checkout extension that composes discount and loyalty helpers over multiple state paths. The safe variant executes through the real direct-WebAssembly path and terminates with
\[
balance=80,\qquad points=8,\qquad cashback=0.
\]
Its protected entry signature must include the transitive balance-decrease and points-increase effects with the expected bounds.

Controlled variants escalate reward magnitude, reverse the balance operation direction, or target unauthorized cashback state. Patch rejects these violations according to Semantic Change Contracts; the first two remain intentionally invisible to the internal target-only ablation, while the target escape is rejected by both.

\subsection{Usage/quota extension case}
A second application case changes domain rather than adding another checkout mutation. It models bounded usage accounting over \texttt{used}, \texttt{remaining}, \texttt{bonus}, and an unauthorized \texttt{admin\_credit} path. The safe variant executes through the same production direct-WebAssembly path and terminates with
\[
used=35,\qquad remaining=85,\qquad bonus=5,\qquad admin\_credit=0.
\]
The protected entry signature must contain transitive usage-increase, quota-decrease, and bonus-increase effects with their declared bounds. Controlled variants exercise magnitude escalation, operation-direction reversal, and target escape under the same internal target-only ablation.

Together, checkout/loyalty and usage/quota form a multi-domain artifact corpus. They are engineering/motivating cases, not a complete plugin sandbox, a real third-party integration study, or empirical evidence about an external extension ecosystem.

\section{Assurance-Cost Evaluation Protocol}
The repository contains a deterministic corpus that separates nested call depth from concrete invocation count. The phase harness measures direct-WebAssembly compilation, precompiled execution, independent validation, end-to-end beta 32 correspondence, and generated certificate-source construction. It records raw samples and artifact sizes.

A second controller adds process isolation. Every independent repetition runs the phase harness in a fresh Node process, retains each raw JSON/CSV report, verifies stable Patch version, exact scenario/source/artifact identity, and normalized runtime/machine identity, then aggregates process medians with minimum, Q1, median, Q3, p95, maximum, mean, median absolute deviation, and interquartile range. The full measured dataset is covered by \texttt{SHA256SUMS}.

Timing evidence is explicitly classified as \texttt{development}, \texttt{hosted-ci}, or \texttt{controlled}. GitHub Actions is forbidden from labelling timing as \texttt{controlled}. A controlled run additionally requires an explicit machine identifier, run label, exact recorded commit equal to \texttt{git HEAD}, and a clean working tree at measurement start.

\paragraph{Current empirical boundary.}
The measurement pipeline is implemented and regression-tested, but this manuscript reports \emph{no controlled paper-quality timing dataset yet}. Consequently it makes no empirical overhead, scalability, or asymptotic-complexity claim. Hosted-CI timing is retained only as reproducibility/regression evidence. Controlled results and statistical models must be added only after measurements on fixed documented hardware are collected and reviewed.

\section{Reproducibility Artifact}
The \emph{Patch Reproducibility Bundle} binds the research artifact to an exact Patch version and 40-character source commit. CI regenerates the finite transitive call-tree certificate, direct-WebAssembly runtime certificate, repeated-call and mixed-guard invocation-frame certificates, semantic-authority report, and both checkout and quota application reports. Non-performance evidence uses \texttt{SOURCE\_DATE\_EPOCH} derived from the source commit so timestamps do not drift with workflow wall-clock time.

The bundle snapshots tracked source plus explicitly regenerated evidence, records byte size and SHA-256 for every included file, verifies those hashes and the version/commit identity, and creates a sorted deterministic tar/gzip envelope with a separate archive SHA-256. Environment provenance is recorded separately from the reproducible claim boundary.

The bundle does not include paper performance results and deliberately does not convert heterogeneous hosted-runner timing into a performance claim.

\section{Portable and Product Artifact Surface}
Patch 0.2.0-beta.35 retains Change IR 0.10 while the product artifact includes a browser-first Patch Studio, a source-backed Window Designer, portable C99, standalone Web builds, direct native GUI backends, and token-free ready/offline runtime paths for supported desktop targets. These capabilities make the artifact easier to inspect and exercise, but they are not primary research novelty claims.

Patch Studio's beta 34 hardening also verifies browser-consumed native runtime templates against a deployment-time SHA-256 manifest derived from GitHub Release asset digests. This is distribution integrity, not platform code signing or a formal security theorem.

Beta 35 adds browser ListBox multi-selection when a ListBox id is backed by persistent list state. Studio App Preview and Standalone Web expose the selected options as a transient text list; persistence still requires an explicit semantic \texttt{change}. Native GUI IR 0.7 does not model persistent list state, so current native Window paths fail closed for that feature rather than silently degrading it. This product behavior does not widen the beta 32 Lean claim.

Editable Window controls preserve the persistent-mutation rule: event-local values and renderer selection/layout state remain transient unless Patch source executes an explicit semantic \texttt{change}.

\section{Limitations and Threats to Validity}
The current artifact has explicit limitations:
\begin{itemize}[leftmargin=*]
\item Patch is not a fully verified compiler; parser semantics outside independently cross-checked supported source/range, guard, and static call-site identity fragments, lowering, runtime capture, validator/frame reconstruction, and WebAssembly execution retain trusted or proof-free boundaries;
\item the independent source/range, guard, and call-site validators are themselves JavaScript implementations rather than verified parsers/evaluators;
\item the mechanized arithmetic/call/runtime fragments are deliberately narrower than the full language and use safe-integer restrictions where exact formal correspondence requires them;
\item GUI/event behavior, richer values, external effects, foreign code, and full native GUI execution are not covered by the beta 32 Lean theorem;
\item the eight security micro-cases and the checkout/quota application cases are controlled artifact cases, not evidence about the prevalence of vulnerabilities, superiority over named prior systems, or behavior in a third-party plugin ecosystem;
\item the target-only security baseline is an internal ablation, not a faithful implementation of prior effect/capability literature;
\item no controlled performance dataset has yet been collected, so there is no measured overhead/scalability result to generalize;
\item the related-work review is structured and primary-source-oriented but is not claimed to be an exhaustive systematic review of every effect, refinement, capability, or state-transition formalism;
\item the candidate novelty is a conjunction of architectural choices and still requires expert/venue scrutiny, even if no reviewed system in the current comparison uses the same default mutation factorization.
\end{itemize}

The highest-value remaining research work is to collect the fixed-machine controlled dataset, analyze scaling with explicit models and dispersion, validate the approach against a genuinely external or third-party extension/integration setting, obtain expert/venue feedback on the architectural conjunction, continue normal pre-submission literature surveillance, and reduce remaining lowering/runtime and out-of-fragment parser trust boundaries where doing so materially strengthens the central claim.

\section{Conclusion}
Patch investigates a language architecture in which ordinary modeled persistent mutation is not merely observed but factored through an explicit semantic Change representation. The same substrate supports operation- and magnitude-aware contracts, history, provenance, and assurance while keeping beginner-facing mutation syntax compact.

The Lean development establishes factorization, signature/policy, range, guarded structured-trace, finite transitive call-tree, and accepted runtime-observation properties for explicit fragments. Beta 32 connects the production direct-WebAssembly path to the finite exact call-tree layer with independently reconstructed invocation frames that distinguish repeated identical calls and preserve different concrete guard-selected traces between repeated identities. Independent source/range and guard validation plus raw-source static call-site binding reduce selected production-extraction trust dependencies, while validator, remaining parser semantics, lowering, capture, and engine correctness remain explicit rather than overstating full verification.

The artifact further supplies semantic-authority ablations, a two-domain checkout/loyalty and usage/quota application corpus, a controlled-measurement protocol, and commit-bound reproducibility packaging. The remaining empirical question is whether the mandatory semantic-mutation factorization provides enough security and engineering value, at acceptable measured cost, to justify the architectural restriction. That question is intentionally left to controlled measurement and genuine external application evidence rather than answered with uncollected results.
