\title{Patch: State-Change Factorization and Semantic Change Contracts for Transparent Mutable Programs}
\author{Mich\'el Nguyen}
\date{Beta 19 research artifact manuscript, August 2026}

\begin{document}
\maketitle

\begin{abstract}
General-purpose languages typically expose persistent mutation through assignment or data-structure-specific update operations, while auditing, undo, provenance, replay, and policy enforcement reconstruct additional semantic structure around those writes. Patch explores the opposite factorization: post-creation persistent mutation is represented and executed through a structured semantic change. A programmer writes \texttt{change score: add 1}; ordinary reassignment is not an alternative persistent-update route. We call the central design property \emph{State-Change Factorization}: every modeled persistent transition factors through a semantic change witness.

Patch derives \emph{Semantic Change Signatures} from this mandatory mutation representation and checks optional \emph{Change Capabilities} constraining target, semantic operation kind, and numeric magnitude. A component may therefore be authorized to increase \texttt{score} by at most 10 while remaining unauthorized to replace or decrease the same location. A Lean 4 core proves State-Change Factorization, Mutation Transparency, Change Signature Soundness for a structured control-flow model, policy containment for accepted formal executions, and integer range-analysis soundness for an explicit arithmetic fragment.

The implementation connects to this core through deliberately separated assurance paths rather than a claim of full compiler verification. For a conservative source subset, an independent raw-source validator---which does not import the production parser or consume the production AST---reconstructs the formal source structure and range claims and compares them with the AST-derived artifact before protected certification. Lean then validates source-to-semantic normalization, evidence decoding, formal signature reconstruction, and policy admission. Separately, the direct WebAssembly backend is checked against an independent Change-IR execution model that reconstructs ordered transitions and concrete semantic effects. Patch also includes a portable C99 backend compile/run tested on Linux, macOS, and FreeBSD. These mechanisms are assurance infrastructure, not firstness claims. The research hypothesis is that mandatory semantic mutation provides a useful common substrate for quantitative state-transition authority, formal reasoning, and runtime tooling without enlarging the beginner-facing language.
\end{abstract}

\section{Introduction}
Mutable programs often need answers beyond the current value of a variable. Debuggers need provenance; user interfaces need undo; replay systems need stable transition records; security mechanisms need to constrain authority. Conventional languages commonly layer these services around writes whose semantic meaning is only partially represented by the language.

Patch asks what changes if the semantic update is primary. Instead of first mutating state and later attaching metadata, a Patch program describes a change that is itself the route to a new persistent state:

\begin{lstlisting}
create number score = 0

change score:
  add 1
\end{lstlisting}

The surface syntax is intentionally small. Internally, the transition can retain target, operation, before/after state, source location, inverse information, provenance, and static authority information.

The same mutation vocabulary supports authority more precise than binary write permission:

\begin{lstlisting}
allow reward:
  score may increase up to 10

make reward(bonus number 0..5):
  change score:
    add bonus * 2
\end{lstlisting}

The policy authorizes a bounded increase. It does not authorize an arbitrary \texttt{set}, even though both operations technically write the same persistent location.

The research question is not whether explicit state changes, effect systems, capabilities, abstract interpretation, source calculi, translation validation, or proof-carrying evidence exist. They do. The question is whether forcing persistent mutation through one semantic representation yields a useful factorization in which execution, quantitative authority, history, provenance, and formal checking reuse the same mutation vocabulary.

This manuscript makes four connected claims about the current artifact:
\begin{enumerate}[leftmargin=*]
\item Patch enforces a language-level factorization in which ordinary post-creation persistent mutation uses structured semantic \texttt{change} operations.
\item The compiler derives operation- and magnitude-sensitive Change Signatures and checks optional Change Capabilities from those mutations.
\item A Lean model proves factorization, signature soundness, policy containment, and integer range soundness for explicit formal fragments.
\item A realistic implementation is connected to the formal artifacts through independent source translation validation and direct-runtime transition/effect validation, while remaining explicit about the parts that are not machine proved.
\end{enumerate}

\section{Language Design}
\subsection{Progressive disclosure}
A beginner can ignore signatures, policies, certificates, and backend details:

\begin{lstlisting}
create number lives = 3
change lives:
  remove 1
show lives
\end{lstlisting}

Advanced machinery derives information from the same source mutation model rather than requiring a separate command/event architecture for ordinary state updates.

\subsection{No persistent-assignment escape hatch}
\texttt{create} introduces a fresh persistent binding. Existing persistent bindings are not subsequently updated with ordinary \texttt{x = e}; state-changing source uses \texttt{change}. This syntactic restriction mirrors the single modeled commit route in the formal machine.

\subsection{Source and semantic operation vocabularies}
The source-facing verbs are \texttt{set}, \texttt{add}, \texttt{remove}, and \texttt{clear}. Static semantic analysis can classify numeric mutations more precisely: \texttt{add 5} is an increase, \texttt{add -5} is a decrease, and \texttt{set 5} is a set. Policies can distinguish these authorities even when they address the same location.

\subsection{Console and GUI code}
Console and GUI programs share the same state/change semantics:

\begin{lstlisting}
create number count = 0

window "Counter":
  text "Count: {count}"
  button "Add" as add_button

when add_button clicked:
  change count:
    add 1
\end{lstlisting}

GUI event execution is implemented but remains outside the current Lean source subset.

\section{State-Change Factorization}
Let persistent state be a map $\sigma : Name \rightarrow Value$, let $\nu(x)$ be the current version of target $x$, and let history be $H=[\delta_1,\ldots,\delta_n]$. A normalized semantic change is
\[
\delta = \langle x,b,n,v,\Delta,v'\rangle,
\]
where $x$ is the target, $b$ and $n$ are base and new versions, $v$ and $v'$ are before and after values, and $\Delta$ is an ordered sequence of semantic operations. Well-formedness requires
\[
applyOps(\Delta,v)=v' \quad\text{and}\quad n=b+1.
\]
The modeled persistent commit is
\[
commit(\delta,\sigma,\nu,H)=
\langle\sigma[x\mapsto v'],\nu[x\mapsto n],H\cdot\delta\rangle.
\]

\paragraph{State-Change Factorization.}
For every state-changing step in the current Lean machine, there exists a well-formed $\delta$ such that the resulting machine is exactly the defined commit of $\delta$.

\paragraph{Mutation Transparency.}
The witnessing change appears in resulting history. Thus a modeled persistent transition cannot occur without an inspectable semantic witness.

These are properties of the formal machine. Production-runtime correspondence is a separate obligation.

\section{Semantic Change Contracts}
\subsection{Change Signatures}
For a recipe $f$, a Change Signature conservatively describes semantic effects:
\[
Sig(f)=\{e_1,\ldots,e_k\}.
\]
An effect includes a target, optional field, semantic operation kind, and optional amount interval. For example,
\begin{lstlisting}
make reward():
  change score:
    add 5
\end{lstlisting}
produces the conceptual summary
\begin{verbatim}
score -> increase by [5,5]
\end{verbatim}

\subsection{Magnitude-aware capabilities}
A policy may authorize selected semantic transitions:
\begin{lstlisting}
allow reward:
  score may increase up to 10
\end{lstlisting}
A protected recipe is rejected if its inferred committed changes are not covered by policy. A \texttt{set} is not interchangeable with an increase, and a proven increase exceeding the bound is rejected.

Magnitude information by itself is not claimed as new. The candidate distinction is that quantitative authority is attached to semantic transition kinds derived from the same mandatory mutation representation through which the state changes.

\section{Formal Core and Machine-Checked Results}
The artifact contains six principal Lean modules: \texttt{PatchFormal}, \texttt{PatchSignature}, \texttt{PatchChecker}, \texttt{PatchEvidence}, \texttt{PatchSource}, and \texttt{PatchRange}.

\subsection{Signature soundness}
For the structured semantic core, Lean proves
\[
Executes(s,r) \Longrightarrow RuntimeChanges(r) \subseteq Sig(s).
\]
The static signature may conservatively contain untaken branch alternatives, but it cannot omit a modeled runtime semantic effect.

\subsection{Policy containment}
If every inferred effect is admitted by policy,
\[
RuntimeChanges(s) \subseteq Sig(s) \subseteq Cap(s),
\]
and therefore
\[
RuntimeChanges(s) \subseteq Cap(s).
\]
The executable verified checker removes the need to assume the middle relation as an unchecked implementation judgment: successful boolean policy checks are proved sound with respect to the relational policy semantics.

\subsection{Source semantic normalization}
The formal source vocabulary preserves \texttt{add/remove/set/clear}. Lean normalizes source operations into semantic effects. For example,
\begin{verbatim}
source add [0,5]      -> increase [0,5]
source remove [0,5]   -> decrease [0,5]
source add [-5,-5]    -> decrease [5,5]
\end{verbatim}
Mixed-sign ranges are outside the certifiable source fragment because they do not have one static semantic direction.

\subsection{Integer range soundness}
For the explicit integer RangeExpr grammar, Lean proves schematically:
\[
\begin{split}
&EnvRespects(\Gamma,\rho)\\
&analyzeRange(e,\Gamma)=I\\
&eval(e,\rho)=v
\end{split}
\quad\Longrightarrow\quad v\in I.
\]
The mechanized fragment includes integer literals, ranged variables, addition, subtraction, negation, and multiplication by a non-negative integer constant. It does not silently cover decimal/floating-point semantics, division, or general multiplication.

\section{Independent Raw-Source Translation Validation}
A central implementation challenge is connecting production source parsing to the formal source artifact without placing the entire JavaScript frontend inside the trusted base.

The production route is
\begin{verbatim}
source bytes -> parser.js -> AST -> formal-source.js -> SourceStmt/ranges
\end{verbatim}
Beta 19 adds a second route:
\begin{verbatim}
source bytes -> source-validation.js -> raw SourceStmt/ranges
\end{verbatim}
The validator does not import \texttt{parser.js} and does not consume the production AST. It is a small indentation-aware recognizer for the formal source subset. It reconstructs source mutation verbs, sequence/branch/literal-repeat structure, ranged recipe parameters, and formal integer range claims directly from source lines.

For each supported entry, certification requires exact structural agreement between the two SourceStmt views and exact agreement between their range claims. Change IR 0.8 records this result as a separate \texttt{sourceValidation} artifact. Negative tests mutate the AST-derived SourceStmt and range claims and require the validator to report disagreement.

This is deliberately framed as \emph{translation validation}. Both paths are executable JavaScript; their agreement is not a machine-checked parser-correctness theorem. Its value is to avoid relying on one production AST/extractor path as the sole source of formal evidence.

\section{Certificate Pipeline}
For a protected recipe in the supported fragment, certificate generation now requires:
\begin{verbatim}
production formalSource supported
raw-source witness supported
SourceStmt equality
range-claim equality
semantic bridge supported
production/formal signature agreement
\end{verbatim}
The generated artifact is bound to the exact source bytes by SHA-256 and records schema versions for source, source validation, evidence, and range data.

Lean then checks:
\begin{verbatim}
RangeExpr -> analyzeRange / rangeAnalysisSound
SourceStmt -> semantic normalization
           -> EvidenceStmt
           -> CoreStmt
           -> inferSignature
           -> compare production signature
           -> verified policy checker
\end{verbatim}
The generated file records that independent source validation passed, but the manuscript does not treat that JavaScript-side fact as a Lean theorem.

\section{Compiled Execution and Runtime Validation}
Patch is no longer an interpreter-only artifact. A direct backend lowers the supported numeric Console subset to WebAssembly. It covers numeric state, \texttt{set/add/remove/clear}, numeric output, arithmetic/comparisons, \texttt{if/else}, literal repetition, acyclic numeric recipes, and ranged parameter guards.

The direct runtime reports a small observation:
\begin{verbatim}
patch.change_number(targetId, before, after)
\end{verbatim}
An independent validator executes the supported Change IR semantics separately, reconstructs the expected ordered transitions, and compares target/order/before/after with observed Wasm execution. A second layer reconstructs concrete increase/decrease/set/clear effects and magnitudes and checks them against static Change Signatures and protected Change Capabilities.

These checks are stronger than comparing only final state, but they remain implementation validation rather than a proof of Wasm lowering correctness.

\subsection{Portable C99}
A second Console backend emits portable C99 for the same conservative numeric subset after support-boundary validation. The generated C preserves ranged parameter guards and a block-level transition hook. Repository gates compile and execute generated C on Linux, macOS, and FreeBSD 15.1. This portability work supports artifact evaluation; C generation is not a novelty claim.

\section{Implementation and Tooling}
Patch Studio is a browser-first PWA. It provides editing, execution, the first Window Designer slice, Change Contract inspection, and Change IR inspection. Browser-local build targets include a standalone Web App, direct Wasm, the bootstrap Wasm carrier, and \texttt{.patchapp}. GitHub-hosted platform runners build Windows/macOS/Linux Console and Window packages from the current editor source; FreeBSD Console uses the C99 backend.

The Window packages currently use a generated desktop player rather than native AppKit/Win32/GTK widgets. Platform packaging is therefore an engineering artifact, not part of the formal or novelty claims.

\section{Evaluation Plan}
The current artifact supports a concrete evaluation plan but does not yet report fabricated performance or user-study results.

\paragraph{RQ1: semantic authority precision.}
Construct examples where write-location permissions cannot distinguish bounded increase/decrease/set/clear authority. Report accepted/rejected contracts and compare the amount of manual runtime checking required.

\paragraph{RQ2: assurance boundary.}
Measure source-validation, certificate-generation, Lean-checking, and runtime-validation cost across a reproducible corpus. Record artifact sizes and failure diagnostics.

\paragraph{RQ3: implementation correspondence.}
Use differential and tamper tests to evaluate how effectively independent source and runtime validators detect disagreement with production artifacts.

\paragraph{RQ4: engineering reuse.}
Compare the implementation needed for history, inverse operations, provenance, preview, and policy checking when these features reuse semantic Changes versus ad-hoc write instrumentation.

\paragraph{RQ5: usability, only if retained as a headline claim.}
A novice study may compare comprehension and mutation errors with a mainstream language, but should be performed only with appropriate study design, consent, and ethics procedures.

\section{Related Work and Claim Boundary}
Patch intersects several mature areas. Plaid makes state change central to object typestate; Worlds reifies and scopes state; effect systems infer and constrain effects; graded/refinement systems can carry quantitative information; object-capability and permission systems constrain authority; abstract interpretation provides sound numeric approximation; event sourcing and reversible systems make updates/history explicit; provenance systems explain executions; translation validation and verified compilers establish implementation assurance; Proof-Carrying Code and certifying compilation attach checkable evidence to programs.

Patch therefore does not claim that first-class state change, effects, capabilities, range analysis, proof-carrying evidence, translation validation, source calculi, WebAssembly compilation, C code generation, undo, or provenance are individually new. The candidate contribution is narrower: persistent mutation is forced through a semantic Change substrate, and operation-/magnitude-aware authority plus tooling are derived from that same mandatory representation.

\section{Limitations and Trusted Boundaries}
The current artifact is not a fully verified compiler. Important limitations are explicit:
\begin{itemize}[leftmargin=*]
\item production parser correctness and independent raw-source parser correctness are not machine proved;
\item beta 19 checks that the two source-extraction paths agree for the supported subset, but agreement is translation-validation evidence;
\item production/direct runtime effect occurrences are not yet connected by theorem to Lean \texttt{SourceExecutes}/\texttt{Executes};
\item direct Wasm and C99 lowering are tested and independently validated in parts, not machine proved;
\item formal call/substitution semantics do not yet cover the full direct recipe implementation;
\item the Lean range theorem covers an integer fragment, not general floating-point runtime arithmetic;
\item GUI event execution, undo/redo, provenance, richer values, external effects, and the full Patch language are outside the current Lean source model.
\end{itemize}

The highest-value next theorem/validation step is to connect independently reconstructed runtime semantic-effect occurrences to the formal execution relation for a useful restricted core.

\section{Conclusion}
Patch explores a simple language-design commitment: existing persistent state changes through explicit semantic Changes. That commitment enables the compiler to derive operation- and magnitude-aware contracts from the same mutation representation used by execution. The current Lean core proves factorization, signature soundness, policy containment, and integer range soundness for explicit fragments. The implementation increasingly connects to that core through separated claims: independent raw-source extraction validation before certification and independent direct-runtime transition/effect validation after compilation.

The artifact deliberately stops short of an end-to-end verification claim. The remaining research problem is now more precise: connect real runtime effect occurrences to formal execution, reduce duplicated untyped lowering through a smaller core IR, and evaluate whether the semantic factorization materially improves security/engineering tasks. If those steps succeed, Patch offers a testable programming-language contribution rather than merely a collection of change-related tools.
